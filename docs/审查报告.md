## 十二、审计方法论（供下轮复用）

1. **别用 Hermes 的 shell 环境判定「编码/环境类修复」**：Hermes 工具 shell 自带 `PYTHONUTF8=1`+`PYTHONIOENCODING=utf-8`+`PYTHONPATH=<hermes>`，会把依赖 locale 的修复判成失败。判定法：`env -u PYTHONUTF8 -u PYTHONIOENCODING` 再跑对照，两种环境结论不同 = 修复绑在环境上，本身就是 bug 信号。
2. **判定「中文是否可读」用布尔 + 落文件，别信屏幕文字**：清掉 `PYTHONIOENCODING` 后 stdout 变 cp936，重定向回 UTF-8 管道会把正确中文显示成乱码。
3. **每类探针用互不干扰的独立路径**：曾被 `create_workspace` 先建出的目录掩盖过 `list_epp_projects` 抛异常（「文件夹不存在」探针假通过）。
4. **探针 helper 形参别叫 `name`/`path`**：与工具参数撞名会在调用处 `TypeError`，用 `tool` 等中性名。
5. **编码问题别靠「先试 UTF-8」的直觉——两种编码可能双向歧义**（2026-09-17 `R4-残` 实测）：GBK 汉字有 **9.2%（1,920/20,902）** 的字节序列**同时是合法 UTF-8**，此时 `try utf-8` 不抛错、**静默解错**（`'专业'`→`'רҵ'`）；反过来 UTF-8 中文字节在 cp936 下也照样能解（`'涓撲笟'`）。**判据**：先认 **BOM**（唯一无歧义信号），无 BOM 时**按来源定顺序**（本机 Windows 生成 → cp936 优先；上游 UTF-8 → 不该进这个 helper）。**「先 utf-8 更保险」是错的直觉**——本报告 §14.1.1 的原稿建议就栽在这上面（已修正）。

#### 14.1.1 `R4-残` 的修正方案（**已实施**，工作树；以下为计算留档）

> ✅ **落地结果**：现名为 `decode_local_text`（`servers/utils.py:110`），顺序 BOM → cp936 → utf-8；三个调用点（`project_reader.read_text`、`signal_chain._acquire_netlist` ×2、`run_turbocharts` stdout/stderr）已改名；`decode_console` **全仓零残留**。套件 **425 passed / 1 skipped**。

```python
# servers/utils.py —— 由 decode_console 改名而来
def decode_local_text(raw: bytes | None) -> str:
    """解码**本机 Windows 生成的文本**（EDI 的 .ep/netlist.log、Qt 工具的控制台输出）。

    ★ 顺序必须 cp936 优先：GBK 汉字有 ~9.2% 的字节序列同时是合法 UTF-8，
      若先试 utf-8 会**静默**解成西里尔/拉丁字母（实测 '专业'→'רҵ'、'一'→'һ'）。
      BOM 是唯一的无歧义 UTF-8 信号，优先识别。
    本函数**不是通用解码器**——不要用它读配置/上游 UTF-8 文本。
    """
    if not raw:
        return ""
    if raw.startswith(b"\xef\xbb\xbf"):
        return raw.decode("utf-8-sig", errors="replace")
    for enc in ("cp936", "utf-8"):
        try:
            return raw.decode(enc)
        except UnicodeDecodeError:
            continue
    return raw.decode("cp936", errors="replace")
```

- **为什么不是「先 utf-8 更保险」**：直觉错在——GBK 源里那 9.2% 的字**不会报错**，只会静静变成别的字；「utf-8 先进」对 UTF-8 源更友好，但**本仓这三个调用点全是本机 GBK 源**。
- **对称陷阱（必须知道）**：翻成「只认 cp936」也不行——UTF-8 文件会静默错（实测 `'专业'` 的 UTF-8 字节按 cp936 解 → `'涓撲笟'`）。所以**顺序必须按来源定**，不能一刀切；BOM 分支覆盖「万一有人存成 UTF-8」。
- **单测（已落地）**：`'专业'.encode('gbk')` ✓、`b'\xef\xbb\xbf' + '专业'.encode('utf-8')` ✓、ASCII ✓、`None`/`b''` ✓。⚠️ **订正我上一版的建议**：那条 `decode_local_text('专业'.encode('utf-8')) == '专业'` **不成立**——cp936 优先下它必然解成 `'涓撲笟'`，**这个断言写不出来**；正确处理是把它记进 docstring 的已知限制（已写：「不是通用解码器」）。**教训：给建议时也要把「这个顺序的代价」一并说清，否则会给出自相矛盾的验收标准。**
- ⚠️ **助手上一轮的建议有同源缺陷**：§十四 原稿（以及 T13 的 `_decode_console`）就是「try utf-8 → except cp936」，即本条缺陷的来源——**这条顺序判据来自实测，不是来自直觉**。

#### 14.1.3 `R17` 修法（唯一剩余 P0 —— 实测证据 + 取舍）

**实测证据（第十四轮复测）**：

| 调用 | 上游 | 我们返回 |
|---|---|---|
| `search_schematic_from_public_library("")` | **422 Bad Request** | `success=false`、`status='FAILED'`、`hint='task_failed'`、`message='网络错误: server replied: Bad Request'`、**顶层无 `error_code` 键** |

| `search_schematic_from_public_library("功放")` | 200 | ✅ `success=true`、`status='SUCCEEDED'`、`count=1`、返回真实数据 → **工具本身可用，修法不碰 happy path** |

**关键事实（改变了修法定位）**：gRPC 信封**根本没有 `error_code` 字段**——实测 `'error_code' in r → False`，顶层只有 `success / completed / outcome_known / task_success / hint / status / message / ...`；失败时 `details` **只回显入参**（`{'search_name': ''}`），**不含任何上游错误码或原因**。所以：

- 「加一处 4xx → `error_code` 映射」**做不到**，除非给信封加字段——那正是 **T5（两套信封）** 的工作；
- 这条的本质是：**上游把参数错误报成了「网络错误」，而我们原样透传**（连 hint 都还是 `task_failed`）。

**处置建议：做 ① + ③，② 并入 T5。**

**① 必做（推荐立刻，~10 分钟）**：本地非空校验。同文件同批 helper 里 `_search_models`（`model_library.py:74`）早就 `require_nonempty(sub_type, label="sub_type")`，`_search_schematic` 却没有——**同文件两处口径不一致本身就是 bug**：

```python
# servers/eda/model_library.py:234
def _search_schematic(search_name: str, task_type: int, timeout_seconds: int) -> dict[str, Any]:
    """按拓扑描述查询原理图库（公共/个人复用，仅 task_type 不同）。"""
    search_name, err = require_nonempty(search_name, label="search_name")   # ← 新增
    if err:
        return err
    return call_grpc(
        task_type,
        {"search_name": search_name},
        timeout_seconds,
        max_timeout_seconds=60,
    )
```

修后信封（`require_nonempty` 实测输出，公共/个人两个工具共用同一 helper）：

```json
{"success": false, "error_code": "INVALID_PARAMETERS", "message": "search_name 不能为空", "hint": "do_not_retry"}
```

→ 空参**根本打不到上游**；agent 拿到的是「补参数」而不是「查网络」。顺带 `None`/非字符串入参也被拦（message 变「必须是字符串」，实测），不必再依赖上游 4xx。**注**：`{"search_name": search_name or ""}` 里的 `or ""` 此后是多余的（可留可删，无行为差异）。

**② 上游 4xx 归一 —— 建议并入 T5，不要现在单做**。若要立刻有改善，**最小且不破坏契约**的改法是**只动 `hint`，不动 `status`**（有调用方按 `status` 分支，改动风险不对称）：

- 复用 `TOOLS_API.md:1775` 已文档化的 `rejected`（对应 status `REJECTED`：「EDI 未受理（参数/权限问题）」）——语义比 `task_failed` 更准，且不新增词表；
- message 前加「上游拒绝（HTTP 4xx，非网络故障）：」，**原文另存 `details['upstream_message']`** 防信息丢失。
- ⚠️ 判别**只能用 message 文本**（服务端没给结构化码），且**必须按 4xx 状态码族**匹配——实测公共库 **422**、个人库 **405**，**别只判 `Bad Request` 字面量**（个人库那条会漏网）。这层脆弱性正是「并入 T5 一起做」的理由：T5 统一失败信封时给 gRPC 家族补 `error_code` 才是正解。

**③ 反馈服务端（治本）**：空 `search_name` 被回 **405 Method Not Allowed** 本身不合理（空串不该走到「方法不允许」）；建议服务端给这两个工具的参数补非空校验，返回**明确的 400 + 可判定错误码**，客户端就不必猜文本。

**④ 明确不做**：不把 `status` 由 `FAILED` 改成 `REJECTED`/新值——EDI 是**先受理再失败**（事件序 `phase=ACCEPTED code=0` → `COMPLETED status=FAILED`），改成「未受理」与事实不符，且会动到按 `status` 分支的既有调用方。

> ④ **实现注意**：`TaskRunner` 用 `concurrent.futures.ThreadPoolExecutor`，**不像 `anyio.to_thread` 那样复制 context**——实测 worker 里读不到请求 Host（`提交者 ctx='127.0.0.1:49378'` → `worker ctx=''`，回落 `http://127.0.0.1:50026`）⇒ 「异步任务结束后自动注册产物链接」会给出**打不开的链接**，需要 **`MCP_PUBLIC_BASE_URL` 兜底**（或把提交时的 Host 存进 task metadata）。整体仍属半天量级（与 §十三 结论一致的"小改"，只是**不是** 3 处的 15 行）。

### 14.6 事件循环冻结（`R45`，2026-09-18 新增；**P0.5**）

**根因**：mcp 1.28 的 `call_fn_with_arg_validation` 里 `if fn_is_async: await fn(...) else: return fn(...)` —— **同步工具直接在事件循环线程里执行**，无 `to_thread`。所以任何 sync 工具执行期间，**整个服务停摆**（下载 / 探活 / 其它会话轮询）。

**修法（每工具 ~3 行，已实测有效）**：

```python
import anyio

def _impl(args...):          # 原同步实现原封不动
    ...

@mcp.tool()
async def some_slow_tool(args...) -> dict:
    """（docstring 不变）"""
    return await anyio.to_thread.run_sync(_impl, args...)   # ← 只加这一层
```

**实测（`edi_tmp/verif38.py` C 组）**：修后工具运行中下载/探活 **5ms → 12ms**（不再冻结）、工具线程变为 `AnyIO worker thread`；**且 `contextvar`（§2.3 的 Host 推导）仍传得进线程**（`base_in_thread = http://<请求Host>`）——修法与产物链接机制**不冲突**。

**优先改哪些**（同步慢工具清单）：`turbocharts_convert`、`compare_simulation_results`、`generate_simulation_report`、`cst_export_snp` / `cst_export_farfield`（走 `cst_runner.run_sync`），以及所有**等 gRPC 响应**的 EDA 工具（`call_grpc` 阻塞等待期间同样冻结；但这类大多是"提交即返回"的异步接口，优先级低）。**异步任务不受影响**（worker 在 `ThreadPoolExecutor`，不占循环）。

> ⚠️ 若选「统一 monkeypatch `Tool.run`」一次覆盖 90 个工具（~15 行），必须回归全部工具 + 确认 contextvar 传递；**不建议**在没有回归预算时一次全改。
