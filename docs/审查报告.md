## 六、工具合并 / 精简路线（服务端接口层）

### 6.1 合并判据（三条**同时**满足才合并）

1. **后端同一个**（同一 gRPC action / 同一 HTTP 端点），差别只在参数；
2. **参数集高度对称**（重叠 ≥ 80%）；
3. **合并后不产生互斥可选参数**（否则只是"数量少了"，agent 更难用）。

> 本节结论均基于**真实签名**（`inspect.signature`，2026-09-16），不再是"看着像"。

### 6.2 逐组结论

| 候选 | 结论 | 依据（真实签名） |
|---|---|---|
| `use_schematic_from_library_create_project` + `..._import` | ✅ **建议合并** → `use_schematic_from_library(file_uuid, mode="create"\|"import", project_path="")` | `(file_uuid, timeout=180)` vs `(file_uuid, project_path, timeout=180)`：**只差一个参数**，完全对称；且当前歧义**有后果**——选错就是「新建工程」还是「导入现有工程」 |
| `simulate_netlist` + `simulate_netlist_with_ads` | ✅ **建议合并** → `simulate_netlist(netlist_path, ads_path="", timeout_seconds=…)` | `(netlist_path, timeout=600)` vs `(netlist_path, ads_path="", timeout=120)`：只差 `ads_path`，且**两处 timeout 默认值不一致（600 vs 120）**，合并正好统一 |
| `search_public_models` + `search_personal_models` | 🔸 **不合并**，只 docstring 互指 | 签名**完全一致**（满足判据 1+2），但**判据 3 不满足**：合成 `library=` 后默认值会造成**静默取错源**（想要个人库却拿到公共库、且返回"成功"）。两个显式名字反而更安全 |
| `search_schematic_from_public_library` + `..._personal_library` | 🔸 同上，不合并 | 同上（签名亦完全一致） |
| `add_ideal_component` / `add_performance_component` / `create_simulation_component` | ❌ 不合并，改**命名族化** | `(project_path, component_type, position)` / `(project_path, component_uuid, position)` / `(project_path, component_type)`：数据源与必填项各异，合并会变成「互斥可选参数」巨型工具 → 改命名族 + docstring 首行点明**来源** |
| `list_schematic_components` / `list_simulation_components` | ❌ 不合并（语义不同），但**参数要对齐** | 前者 `(summary_only=False, limit=0)` **无 offset**；后者 `(offset=0, limit=100, include_hidden, summary_only)` **有** → 以后者为模板统一 |
| `export_project_netlist` / `tr_get_project_netlist`；`list_schematic_components` / `tr_query_schematic_components` | ❌ 不合并 | TR 版是版本化可追溯工作流（网表修订不覆盖原网表），重叠是**故意的**；两组 docstring 各加一句「TR 版用于可追溯流程，普通场景用基础版」 |
| `get_simulation_async_status` / `get_simulation_async_result` | ❌ 不合并 | 签名虽同，但一个是轮询、一个取大 payload；合并会把大结果带进轮询路径 |
| `open/close_edi_project` vs `open/close_hfss_project`；`cst_*_query` vs `get_hfss_*` vs `get_*_async_status` | ❌ 绝不合并 | 不同工具链后端；后者的真问题是**命名漂移**，不是数量 |

**净结果：90 → 88**（只减 2 个）。

### 6.3 比合并更划算的三件事（降认知成本，不动接口）

1. **命名族化**：同族工具统一前后缀（`add_*` / `list_*` / `tr_*`），docstring 首行写清**来源 / 后端**——解决"该选哪个"。
2. **参数语义对齐**：列/搜类统一 `limit` / `offset` / `summary_only` 三元组，并把默认值口径写进 docstring。
3. **`docs/TOOL_INDEX.md` 分组渲染**（已自动生成）：按「工程管理／仿真／分析导出／TR／软IP／模型库」分组——**发现成本靠分组 + 命名解决，不靠删工具**。

### 6.4 合并操作提示（若执行 6.2 的两个合并）

- **属于 breaking change**：保留旧名 alias（旧名内部转调新名，docstring 标「已废弃，请用 X」），否则现有客户端会话会突然找不到工具。
- **同步点**：`scripts/gen_tool_index.py` 重生成 `docs/TOOL_INDEX.md`、`tests/test_tool_index.py` 断言、`docs/TOOLS_API.md`、`servers/chat/index.html` 的工具 UI 映射（若涉及）。

### 6.5 需优化（保留但改进）

- **异步查询命名三套不一致**：CST `*_query` / HFSS `get_*_status` / EDA `get_*_async_status`；且 `cst_export_snp` 无 query、`cst_export_farfield` 有 query（不对称）。
- **搜索/模型库分页**：`search_public_models` / `search_personal_models` 的 `limit` 已修好并实测生效（-99.6% 体积），但仍**无 `offset`**、上游响应无 page/total 字段；软 IP 的 `search_*_soft_ip_models` 已由服务端自动合并分页，可作参照实现。
- **体积口径**：`get_model_category_params` 全量约 **42KB**（默认已精简，省 88%）；**真正的上下文大头是模型搜索**（sub_type 62 单次 **391 条 / 428KB**），已由 `limit` 截断。

## 十一、整体判断与 ROI 排序（助手的建议）

> 把前面各节的结论收敛成一句可执行的话。

**一句话**：**精简的重点不是删代码行数，而是删掉「多套并行的语义」（队列、参数名、信封、键语言、清单）；加强的重点不是加功能，而是给已有东西补上自动校验、分页与统一的机器可读契约；合并工具的收益远小于修错误契约。**

**ROI 阶梯（从高到低）**

| 梯队 | 做什么 | 为什么排这里 |
|---|---|---|
| **P0** | **无**——「agent 必然踩且无法自愈」的行为类 bug 已清零（T1–T4 / T6 / T11 / T13–T16 逐条实测闭环） | 上一轮为此设的 P0 已清空；剩下都是契约/风格/文档/结构类 |
| **P1** | **契约与信封对齐**：T5（先统一失败信封）、T3-尾（两处待拍板）、`list_*` 参数对齐、P2-5（`Out`/`EXCLUDED_TYPES`）、顺手三清 N1/N2/B9/B19 | agent 每次调用都经过这一层，且都是低风险局部改动 |
| **P2** | **测试与交付可信度**：S4（`skipif` 分类 + 403 断言 + 交付口径改 `N passed (M 真跑 / K skip)`） | 不修这个，后续每轮审计的「passed」都不可信 |

| **不做** | ① 为"数量好看"合并（90→88 已足够，别追 50）；② 删「词典/公共 API/防御冗余」类（`ERROR_CODES`、`TaskRunner.count/prune`、`eda/__init__` re-export、`load_dotenv` 重复、PE 解析器）；③ 动真实信任边界（`report/generator` 校验链、`chat/routes` 上传限制、`_prepare_parameters` 校验） | 已逐条定性，见 §四末「已定性保留」 |

**三条方法论（供后续审计复用）**（更细的一版见 §12.5）

1. 判定"死代码"要区分 **死代码路径**（函数/字段/分支 → 删）与 **词典/公共 API/防御数据**（查表完整性/对外契约/安全冗余 → 留）。
2. 任何"看起来像"的结论都要用**真实签名/真实调用**复核——多轮以来的改判（`search_*` 不合并、`limit` 静默失效、`HANDOVER` 计数误报、`compare_simulation_results` 从未可用）全部来自实测而非阅读。
3. **探针测写入类工具时先用不存在的路径/占位值**；且**每类探针用互不干扰的独立路径**——曾被 `create_workspace` 先建出的 `C:/__hermes_probe__/` 掩盖过 `list_epp_projects` 的抛异常（「文件夹不存在」探针假通过）。另外：探针脚本的 helper 形参别叫 `name`（与 `create_project(name=…)` 撞名会 `TypeError`）。

**对已修项的观察（留档一行）**：本轮及上一轮 T1–T4/T6/T11 的修法多为**在入口或 helper 处一次收敛**（`require_file` / `call_project_grpc` catch / 统一 `error_response`），而非逐工具 try；T3 的校验还**保留了正常路径不被误拦**（新路径仍可创建，实测过）——这正是上一轮建议的 DRY 路线，收尾成本因此很低。

### 12.2 需要你拍板（我给倾向 + 理由）

### 12.3 中期（有收益，但要动一点结构）

**T5 两套信封 —— 建议分两步，别一次动完**

1. **先统一「失败」信封**（低风险、收益最大）：所有家族失败一律 `error_response(...)`（ANSYS 已迁完）→ agent 判失败只看 `success`，不再猜家族。
2. **「成功」信封暂不合并**：EDA gRPC 家族 `details` 里带 `status/task_success/outcome_known/hint`，本地/TR 家族没有任务语义——**强行统一只会造出「永远为 null 的字段」**。建议改为在 docstring 首行写清「本工具是本地计算，不产生 task 信封」，比统一字段省事得多。

**S1 契约口径统一 —— 用别名过渡，别一步改签名**：先 `originalid_list` **加别名** `original_ids`（两者都收）→ docstring 只写新名 → 下一轮再删旧名。直接改签名会打断现有会话/脚本。

### 12.5 审计方法论补充（本轮踩到的，供下轮复用）

1. **⚠️ 别用 Hermes 的 shell 环境判定「编码/环境类修复是否生效」**：Hermes 工具 shell 自带 `PYTHONUTF8=1` + `PYTHONIOENCODING=utf-8` + `PYTHONPATH=<hermes>`，会把**依赖 locale** 的修复判成失败。**判定法**：`env -u PYTHONUTF8 -u PYTHONIOENCODING` 再跑一遍对照——**两种环境结论不同 = 修复绑在环境上，这本身就是一条 bug 信号**。
2. **判定「中文是否可读」要用布尔 + 落文件，别信屏幕文字**：清掉 `PYTHONIOENCODING` 后 Python 的 stdout 也变 cp936，重定向回 UTF-8 管道会把**正确**的中文显示成乱码——本轮被这个假象骗过一次。
3. **每类探针用互不干扰的独立路径**：曾被 `create_workspace` 先建出的 `C:/__hermes_probe__/` 掩盖了 `list_epp_projects` 的抛异常（「文件夹不存在」探针**假通过**）。
4. **探针 helper 的形参别叫 `name`/`path`**：与工具参数撞名会在调用处直接 `TypeError`（本轮自伤两次）。用 `tool` 之类的中性名。
5. **「看起来像」的结论一律真调复核**：本轮 T13 从「已修」改判「半修」、T11 从「文档漂移」改判「工具 100% 不可用」、`metrics=0.0` 从「疑似 bug」澄清为「真数据（两份 RAW 在 0/2/4GHz 都是 -100 底噪）」——全部靠真调才浮现。
