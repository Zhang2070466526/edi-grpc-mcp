## 十、接口收敛路线（工具合并，降认知成本）

> 结论均基于**真实签名**（`inspect.signature`，2026-09-16）。

**合并判据（三条同时满足才合并）**：① 后端同一个（同一 gRPC action / HTTP 端点）；② 参数集高度对称（重叠 ≥ 80%）；③ 合并后不产生互斥可选参数。

## 十二、审计方法论（供下轮复用）

1. **别用 Hermes 的 shell 环境判定「编码/环境类修复」**：Hermes 工具 shell 自带 `PYTHONUTF8=1`+`PYTHONIOENCODING=utf-8`+`PYTHONPATH=<hermes>`，会把依赖 locale 的修复判成失败。判定法：`env -u PYTHONUTF8 -u PYTHONIOENCODING` 再跑对照，两种环境结论不同 = 修复绑在环境上，本身就是 bug 信号。
2. **判定「中文是否可读」用布尔 + 落文件，别信屏幕文字**：清掉 `PYTHONIOENCODING` 后 stdout 变 cp936，重定向回 UTF-8 管道会把正确中文显示成乱码。
3. **每类探针用互不干扰的独立路径**：曾被 `create_workspace` 先建出的目录掩盖过 `list_epp_projects` 抛异常（「文件夹不存在」探针假通过）。
4. **探针 helper 形参别叫 `name`/`path`**：与工具参数撞名会在调用处 `TypeError`，用 `tool` 等中性名。
5. **编码问题别靠「先试 UTF-8」的直觉——两种编码可能双向歧义**（2026-09-17 `R4-残` 实测）：GBK 汉字有 **9.2%（1,920/20,902）** 的字节序列**同时是合法 UTF-8**，此时 `try utf-8` 不抛错、**静默解错**（`'专业'`→`'רҵ'`）；反过来 UTF-8 中文字节在 cp936 下也照样能解（`'涓撲笟'`）。**判据**：先认 **BOM**（唯一无歧义信号），无 BOM 时**按来源定顺序**（本机 Windows 生成 → cp936 优先；上游 UTF-8 → 不该进这个 helper）。**「先 utf-8 更保险」是错的直觉**——早期给的建议就栽在这上面；现实现见 `servers/utils.py::decode_local_text`（BOM → cp936 → utf-8）。

6. **「看起来像」的结论一律真调复核**：多轮改判（`search_*` 不合并、`limit` 静默失效、`compare_simulation_results` 从未可用）全来自实测而非阅读。本报告的多处改判（`search_*` 不合并、`limit` 静默失效、`compare_simulation_results` 从未可用、`R19`「永远排队」实为「最多阻塞 TTL」……）**全部来自实测、而非阅读**——**子代理读码的命中率约 90%，但那 10% 会误导修复方向**。能真调的一律真调（broken symlink、GBK 文件、`timeout=1`、坏目录都是真造出来的），比读码强得多。

7. **功能性问题必须真调，但先钉死运行态——否则会把竞态写成缺陷**（2026-09-21 本轮）：逐条 `curl` 打 `/mcp` 真调 **28 个工具 + 4 个协议方法**，结论是**无功能性失效**（要么返回真数据，要么回干净统一信封）。踩到的坑：EDI 恰在扫描中途启动（`50055` pid 使 `/ready` 由 `offline` 变 `online`），`get_service_status` 报 `channel_state: unknown` 而资源报 `ready`，一度被写成「三处口径矛盾」→ 复核为**竞态**（状态字段是惰性缓存，见 §13.6）。**下轮复用**（新增：**缓存型字段别当实时值** —— `get_service_status.channel_state` 在首次 gRPC 调用前恒为 `unknown`（同期资源报 `ready`），我一度判成「竞态」；正确判法是**先做一次真调用再读**，`unknown`→`ready` 即证明是惰性缓存）：
