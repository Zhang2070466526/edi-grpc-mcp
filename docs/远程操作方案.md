### 0.2 术语

| 概念 | 定义 |
|---|---|
| **主机**（= 客户端机）| **你下命令的那台**：跑 Claude Code / Hermes / 自定义 agent，只发 MCP 指令。**不装任何服务、不装 EDA** |
| **远程机**（= 引擎机 / 服务机）| 装了 **AEDT / CST / ADS**，并且**放一个「通信 + 执行」程序**的机器：**软件的启动与工具的执行都发生在这里** |
| **那个「通信程序」= MCP 服务本身** ★ | 开发机 = `start_servers.py`；**现场 = `edi_mcp_server.exe`**（打包产物 `dist-win7/edi-mcp/`）。一个程序两用：① 对外提供 MCP over HTTP（主机的指令走这里进）；② 对内驱动 AEDT（COM）/ CST（本机 API）/ EDI-ADS（gRPC）并读写本机文件 |
| **客户端** | **主机**上跑的 agent 进程，经 HTTP 连远程机的 `/mcp` |
| **任务** | 一次仿真/导出/求解等操作，有 `task_id` 与状态机（§六）|

> 🔑 **原则**：主机远程连接其对应的多台远程机；**启动软件**（`launch_edi` / `launch_aedt` / `open_hfss_project`）**与执行工具**（仿真、出图、报告、抗烧毁…）**都在对应的远程机上**，主机不参与执行。「主机 ↔ 远程机」= **MCP 客户端 ↔ MCP 服务端**。
⇒ 因此装机量：**主机侧零安装**（只配一个 URL）；**远程机侧装一个程序**（那个 exe/服务 —— 它同时就是通信端和执行端，不需要再装别的东西）。

### 0.5 部署形态与链路（一张图看懂）

```
主机（你坐这、跑 Hermes / Claude Code —— 只发指令，零安装）
  └─ MCP 客户端（agent 自带，不起服务、不监听端口）
        │   HTTP:  http://<远程机IP或主机名>:50026/mcp
        ▼
远程机（装 AEDT / ADS / CST 的那台 —— 只装这一个程序）
  └─ MCP 服务 = edi_mcp_server.exe      ← 唯一的「通信 + 执行」程序（手动启动）
        ├─ COM（本机）      → AEDT / HFSS
        ├─ 官方 API（本机）  → CST
        ├─ gRPC → EDI/ADS（本机 50055）
        └─ 本机文件读写      → 工程 / RAW / 产物 ──▶ 回传下载 URL（/documents/{token}）
```

| 说法 | 对不对 |
|---|---|
| MCP **服务**部署在**远程机**（一个 exe，手动启动）| ✅ **是** |
| **主机**上的 agent 作为 MCP **客户端**，连远程机的 `/mcp` | ✅ **是**（改一行 URL + 新开会话）|
| 主机上也部署一个 MCP 服务 | ❌ 不是（主机上只有 agent）|
| 「本机的 mcp 服务连远程的 mcp 服务」（两级代理）| ❌ 本期不做（P5 可选，§ 见形态对比）|

**为什么必须这样**（不是可选的玩法）：AEDT 靠 `GetActiveObject` 的**本机 COM** + `subprocess.Popen(ansysedt.exe)` 的**本机进程**；CST 靠 `cst.interface` 的**本机 API**；工具层还有本机文件语义（`raw_path` 必须在**服务所在机器**的会话目录内）。⇒ **服务不贴着软件就够不着**。

**已实测**（`verif29`/`verif30`/`verif33`）：服务绑 `0.0.0.0` 后从**另一台机器**访问 → `/ready` 200、真 MCP 客户端 `tools=90`、`call_tool` 成功、产物 URL 可下载；同时本机 `127.0.0.1` 仍正常（本机用法不受影响）。

### 0.7 一句话结论

远程 = ① `--host 0.0.0.0`；② `transport_security` 动态枚举（漏了它 `/mcp` 一律 **421**）；③ 产物链接按**请求 `Host`** 推导（主机不固定）；④ 白名单远程自动忽略 + 探针保留；⑤ **`fetch_artifact`**（产物取回）；⑥ Host 校验；⑦ `MCP_PUBLIC_BASE_URL` 兜底。再加 **P0.5**：慢同步工具 offload + 加锁（否则下载/轮询被冻结）。**鉴权本期不做**、**地址零配置**、**sqlite 只用来扛重启**。多引擎机调度是另一个量级，由客户端配多地址解决——**服务端永远不需要调度器**。

## 一、为什么不能「直接远程操作软件」

| 软件 | 驱动方式 | 能否跨机 |
|---|---|---|
| AEDT / HFSS | COM（`win32com.GetActiveObject` 附着本机实例）+ subprocess 起 `ansysedt.exe` | ❌ COM 是机器本地 IPC |
| CST | `cst.interface.DesignEnvironment.connect_to_any_or_new()` 连本机 | ❌ 官方 API 只连本机 |
| ADS（经 EDI） | gRPC（`EDA_GRPC_SERVER`，默认 `127.0.0.1:50055`） | ✅ gRPC 可远程，但工具层仍做本机文件读写 |

**要求**：软件必须被「引擎机上的进程」驱动。
**约束**：AEDT/CST 的 COM/本地 API 决定了「驱动进程必须与软件同机」。
**方案**：MCP 服务跑在引擎机，MCP 协议（streamable-http）负责跨机。→ 由此推出**原则**：**软件的启动**（`launch_edi` / `launch_aedt` / `open_hfss_project`）**与工具的执行**（仿真/出图/报告/抗烧毁…）**都发生在引擎机上**，**主机只负责发 MCP 指令**，不装软件、不启动软件、不直接操作 EDA。

### 2.1 ① `host` 硬编码

**现状**：`start_servers.py:205` 写死 `host = "127.0.0.1"`；`main()` 只有 `--transport` / `--port`（实测 `--help`）。

**修法**：`main()` 加 `--host`（**默认仍是 `127.0.0.1`** → 本机模式零变化）；`settings.py` 加 `mcp_bind_host`；`_run_http_server(host, port)` 透传；`uvicorn.run(..., host=host)`。

**验收**：`--help` 里出现 `--host`；**不带参数**启动后 `curl http://127.0.0.1:50026/ready` 正常。

### 2.2 ② `transport_security`：非环回一律 421 ★

**实测（把 app 绑到 `0.0.0.0` 后从本机网卡访问）**：

| 请求 | 结果 |
|---|---|
| `POST /mcp`，`Host: 127.0.0.1:PORT` | ✅ 200 |
| `POST /mcp`，`Host: localhost:PORT` | ✅ 200 |
| `POST /mcp`，`Host: 192.168.0.58:PORT`（LAN IP）| ❌ **421 `Invalid Host header`** |
| `POST /mcp`，`Host: DESKTOP-1NH03PE:PORT`（**主机名**，★ 实测）| ❌ **421**（小写主机名同样 421 → **大小写敏感**）|
| 真 MCP 客户端 → `http://192.168.0.58:PORT/mcp` | ❌ 握手失败 |
| 真 MCP 客户端 → `http://127.0.0.1:PORT/mcp` | ✅ `tools=90` |

**根因**：`mcp 1.28` 的 `FastMCP.__init__` 只在 host ∈ {`127.0.0.1`,`localhost`,`::1`} 时自动构造 `TransportSecuritySettings(allowed_hosts=[127.0.0.1:*, localhost:*, [::1]:*])`；本仓在 `servers/__init__.py` 的 **import 期**就构造了 FastMCP，`start_servers.py` 是**构造后**才改 `mcp.settings.host` → **该字段不会重算**。

**修法（实测通过）**：在 `starlette_app = mcp.streamable_http_app()` **之前**显式覆盖：

**落地实现**（与本节早期设计稿的差异已在下方逐条说明）——枚举与允许列表构建在 `servers/utils.py`，装配在 `start_servers.py`：

```python
# servers/utils.py —— 实际落地（节选）
_LOOPBACK_HOSTS = ("127.0.0.1", "localhost", "[::1]", "::1")

def local_host_names() -> list[str]:
    """环回 + 全部网卡 IP + 主机名/FQDN（含大小写）。"""
    hosts: list[str] = list(_LOOPBACK_HOSTS)
    import psutil                                    # ★ psutil：getaddrinfo(gethostname) 会漏网卡
    for _name, addrs in psutil.net_if_addrs().items():
        for a in addrs:
            if not a.address:
                continue
            if a.family == socket.AF_INET:
                hosts.append(a.address)
            elif a.family == socket.AF_INET6:
                addr = a.address.split("%", 1)[0]     # 去 Windows 的 %scope 后缀
                if addr != "::1":                     # ★ 非环回 IPv6 也进（[fe80::x] 形式）
                    hosts.append(f"[{addr}]")
    hn = socket.gethostname()
    hosts += [hn, hn.lower(), hn.upper()]             # ★ 主机名（含大小写）也必须进
    fqdn = socket.getfqdn()
    if fqdn and fqdn not in hosts:
        hosts += [fqdn, fqdn.lower()]
    return list(dict.fromkeys(h for h in hosts if h))

def build_transport_security(extra_hosts=()):
    from mcp.server.transport_security import TransportSecuritySettings
    names = local_host_names()
    for h in extra_hosts:                             # MCP_EXTRA_ALLOWED_HOSTS 手工补
        if h.strip() and h.strip() not in names:
            names.append(h.strip())
    patterns = [p for h in names for p in (h, f"{h}:*")]   # 裸名 + 裸名:* 两种模式
    return TransportSecuritySettings(
        enable_dns_rebinding_protection=True,         # ★ 绝不关闭
        allowed_hosts=patterns,                       # allowed_origins 保持为空（不放行浏览器跨源）
    )
```

```python
# start_servers.py —— 必须在 streamable_http_app() 之前（构建 app 时读该设置）
extra_hosts = [h.strip() for h in (_cfg.mcp_extra_allowed_hosts or "").split(",") if h.strip()]

...
starlette_app = mcp.streamable_http_app()             # ← 之后再 add_middleware
```

**本机实测**：`local_host_names()` = `['127.0.0.1', 'localhost', '[::1]', '::1', '192.168.0.58', 'DESKTOP-1NH03PE', 'desktop-1nh03pe']` → **14 条模式**（主机名本身全大写，故大小写两写法去重；另有 1 条非环回 IPv6 `fe80::…` → **16 条**）。VPN 网卡 `10.111.222.1` 当前**适配器未启用**故未出现 —— 这正是动态枚举的本意（适配器起来就自动进列表），不靠 `MCP_EXTRA_ALLOWED_HOSTS` 兜。

**与本节早期设计稿的 4 处差异（均已实测）**：

| 设计稿 | 实际落地 | 为什么改 |
|---|---|---|
| `allowed_origins=["*"]` | **`allowed_origins=[]`**（保持 SDK 默认） | `[]` 会让浏览器带 `Origin` 访问 `/mcp` 得 403；MCP 客户端（Hermes/Claude Code）**不发 `Origin`**，收紧无代价 |
| 只枚举 IPv4 | **IPv4 + 非环回 IPv6（方括号形式）** | 本机实测存在 `fe80::…`；只收 IPv4 时用 IPv6 访问会 421 |
| 过滤 `169.254.` 链路本地 IPv4 | **不过滤** | 该地址只可能指向本机自身网卡，放行不扩大攻击面；过滤反而在同链路隔离网里连不上 |
| 每 host 只给 `f"{h}:*"` | **裸名 + `:*` 两种** | SDK 用 `host.startswith(base + ":")` 匹配，不带端口的 `Host` 边界情形靠裸名模式覆盖 |

**必须守的两条（都有实测支撑）**：

1. ⚠️ **不要图省事改成 `enable_dns_rebinding_protection=False`**：实测此时伪造 `Host: evil.example.com` 会被**放行**（`/health` 200、`POST /mcp` initialize **200**）→ 见 §2.3 的链接污染风险。走 `allowed_hosts` 路线时，进入 `/mcp` 的 `Host` 必然在白名单内。
2. ⚠️ **枚举必须完整**：实测 `socket.getaddrinfo(socket.gethostname(), None, AF_INET)` 在本机**只回 `192.168.0.58`，漏掉 VPN 网卡 `skyline-vpn-ethernet / 10.111.222.1`**；且**白名单只列 IP 时用主机名访问会被 421**。⇒ 用 `psutil` + 带主机名，并留 `MCP_EXTRA_ALLOWED_HOSTS` 手工补。**排查口诀：看到 421 就把客户端用的那个 IP/主机名补进去。**

**边界**：该校验**只作用于 `/mcp`**（由 StreamableHTTP 会话管理器持有）；`/health`、`/metrics`、`/ui`、`/tools/list`、`/upload`、`/chat` **不走它**（实测伪造 Host 也 200）→ 这既是「远程能拉产物」的前提，也是暴露面的来源（§三）；**不要在这些路由上做按 Host 判断的安全决策**。

**验收**：`Host=<本机 IP>` → 非 421；`Host=<本机主机名>` → 非 421；`Host=evil.com` → **421**。

### 2.3 ③ 产物链接地址：按**请求 `Host`** 推导 ★

**现状**：`servers/utils.py` 的 `get_server_base_url()` 把 `0.0.0.0`/`::` 强映射成 `127.0.0.1`（实测返回 `http://127.0.0.1:50026`）→ 远程主机拿到的产物链接指向**它自己的 localhost**。

**要求**：主机用什么地址连远程机，链接就用什么地址（主机/网段都不固定 → 不能写死）。

**落地实现**（`servers/utils.py` 提供上下文 + 推导，`start_servers.py` 负责采信校验）：

```python
# servers/utils.py —— 实际落地
_request_base_url: ContextVar[str] = ContextVar("mcp_request_base_url", default="")

def set_request_base_url(base_url: str) -> None:
    _request_base_url.set(base_url)

def current_request_base_url() -> str:
    return _request_base_url.get()

def get_server_base_url() -> str:
    """优先请求 Host；无上下文时回落到启动时 host:port（本机模式行为不变）。"""
    base = _request_base_url.get()
    if base:
        return base
    with _lock:
        host, port = _address.host, _address.port
    public_host = "127.0.0.1" if host in ("0.0.0.0", "::") else host
    return f"http://{public_host}:{port}"
```

```python
# start_servers.py —— 允许列表内的 Host 才采信（Host 校验在这里，不在 get_server_base_url 里）
class RequestBaseURLMiddleware(BaseHTTPMiddleware):
    def __init__(self, app, allowed_bases: set[str]) -> None:
        super().__init__(app)
        self._allowed = allowed_bases                      # 来自 local_host_names() + 额外 host

    async def dispatch(self, request: Request, call_next):
        host = request.headers.get("host", "")
        if host and len(host) <= 255 and host_without_port(host).lower() in self._allowed:
            set_request_base_url(f"{request.url.scheme or 'http'}://{host}")
        return await call_next(request)
```

**⚠️ 为什么必须校验 Host（实测）**：`Host` 是客户端自己写的；关保护时伪造 `Host: evil.example.com` 会被放行 → 链接被污染成 `http://evil.com/documents/<token>`（等于把下载权递出去）。所以**只有 Host ∈ 本机允许列表时才写进上下文**，否则 `get_server_base_url()` 走回落。

**实测（`verif42.py`，真实子进程起服务）**：

| 例 | 输入 | 输出 |
|---|---|---|
| ① | 客户端连 `192.168.0.58:50926` 调 `open_document(mode="link")` | **`http://192.168.0.58:50926/documents/<token>`** ✅ 且 `GET` → **200 字节一致** |
| ② | 同机客户端连 `127.0.0.1:50926` 调同一工具 | `http://127.0.0.1:50926/documents/<token>` ✅（本机行为不变）|
| ③ | 伪造 `Host: evil.example.com` | **不采信**，回落 `http://127.0.0.1:<port>` ✅（单测 `test_forged_host_falls_back_to_configured_address`）|
| ④ | 无请求上下文（异步 worker / stdio） | 回落 `http://127.0.0.1:<port>`，`0.0.0.0` 仍映射 `127.0.0.1` ✅（`tests/test_utils.py` 既有断言未变）|
| ⑤⑥⑦ | 配 `MCP_PUBLIC_BASE_URL` / `MCP_PUBLIC_SCHEME` | ⛔ **本期未落** —— 这两个 env 还没加，反代/https 场景暂不可用 |

**⚠️ 为什么异步场景仍需 `MCP_PUBLIC_BASE_URL` 兜底（实测）**：在请求上下文里提交 `TaskRunner` 任务，**worker 线程里 `contextvar` 是空的**（`提交者 ctx='127.0.0.1:49378'` → `worker ctx=''`），因为 `TaskRunner` 用 `concurrent.futures.ThreadPoolExecutor`，**不像 `anyio.to_thread` 那样复制 context**。⇒ 将来做「异步任务结束后自动注册产物链接」时，链接会回落成 `127.0.0.1`；本期同步工具不受影响，但该变量**必须在做 P0.5 异步产物之前补上**。

**实测（穿透性）**：middleware 设的 `contextvar` **能进同步工具**（环回请求 → `127.0.0.1:PORT`；LAN 请求 → `192.168.0.58:PORT`）；**两个客户端并发调用无串扰**。

**⚠️ 实现坑**：`servers/token_registry.py` 是 `from servers.utils import get_server_base_url`（**按名字绑定**）→ 必须**在 `servers/utils.py` 内部**改这个函数；从外部替换 `utils.get_server_base_url` 会让 `token_registry` 静默继续用旧函数。
### 2.4 ④ 进程白名单：远程留空 + 探针保留

**现状**：白名单靠「同机 TCP 表反查来源进程」，`find_client_process` 按 `conn.laddr.port == client_port` 匹配——**该假设只对同机连接成立**（远程客户端的源端口不在本机 TCP 表里）→ 返回 `('','')` → **403 `PROCESS_UNKNOWN`**（码中注释也默认了「laddr 是客户端地址」）。且它**只保护 `/mcp`**。

**修法**：远程模式（`--host` 非环回）下**自动忽略** `MCP_ALLOWED_PROCESSES`（= 不拦截，无需改 `.env`）；此时挂的是 `ProcessProbeMiddleware`（只打印来源进程）→ **保留它**（`MCP_PROBE_ENABLED` 默认 `1`），因为**无鉴权下它是唯一的「谁在连」线索**；建议顺手补一行 `request.client.host`（远程反查不到进程，日志里 `exe=`/`cmd=` 会空）。

**验收**：留空时主机可正常连；服务启动日志/运行日志能看到探针输出。

**落地实测（`verif42.py`）**：`MCP_ALLOWED_PROCESSES=""` 时启动打印 `Probe:  process probe enabled …` 且 LAN 调用全部放行；`MCP_PROBE_ENABLED=false` 时打印 `Guard:  disabled (no whitelist, probe off)` —— 开关生效、默认开。

### 2.5 缺失能力：产物通道（**新增 `fetch_artifact`**）

`.snp` / `.raw` / 任意非办公格式产物**当前完全拿不到**（`open_document` 的扩展名白名单只有 10 种办公格式，实测 `.s2p`/`.raw` → `UNSUPPORTED_FORMAT`）→ **P0 第 ⑤ 项**，实现与实测见 **§九**。

## 三、接入控制与安全（本期：直接访问）

### 3.0 现状：暴露面（实测）

**本服务没有 token / 账号体系**（代码域已无 `MCP_API_KEY`：`servers/`、`start_servers.py`、`scripts/`、`tests/`、`proto/` 零命中）；唯一的接入控制是进程白名单 `MCP_ALLOWED_PROCESSES`，而它**只作用于 `/mcp`**：

| 路由 | 受白名单保护 | 说明 |
|---|---|---|
| `POST /mcp` | ✅ **唯一受保护** | 未命中 → 403（`PROCESS_UNKNOWN` / `PROCESS_NOT_ALLOWED`）|
| `/tools/list` | ❌ | **直接返回全量工具名 + 描述**（实测 200）|
| `/metrics` | ❌ | 匿名可拉（实测 200）|
| `/ui`、`/` | ❌ | 浏览器界面（实测 200）|
| `POST /upload`、`POST /chat` | ❌ | 端点可达（实测 400，说明已进路由）|
| `GET /images/{token}`、`GET /documents/{token}` | ❌ | 靠**不可猜 token**（`token_urlsafe(24)`，10 分钟）自我鉴权 —— **刻意设计**，见 §九 |

**两条补充事实（实测）**：① `transport_security` 的 Host 校验**只作用于 `/mcp`**，上表其余路由**不经过**它；② 白名单**留空 = 不拦截**，此时挂的是 `ProcessProbeMiddleware`（打印来源进程 + 对每条 `/mcp` 请求做一次 `psutil.net_connections()` 全表扫描）。

### 3.1 本期决策：**不做鉴权，直接访问**（2026-09-18 用户决定，内网可信）

**理由**：① 内网、主机与远程机都在自己手里；② 本机防火墙三档（域/专用/公用）**实测全是关闭状态** ⇒「防火墙兜底」不成立，任何方案都得靠应用层或网段；③ 需求是「先用起来」。

**因此远程 = 无鉴权开放**，残余风险与缓解：

| 残余风险 | 缓解 |
|---|---|
| 能连上远程机的人可调**任意工具**（含 `clear_schematic`、跑仿真、`open_document(mode="local")`）| 网段隔离、只放可信内网（不做技术边界，属**已接受**）|
| `/tools/list`、`/metrics` 匿名可枚举 | 同上；建议 `/metrics` 不放敏感信息 |
| `fetch_artifact` 可下载远程机上**任意文件**（实测 `C:/Windows/win.ini` → 200）| **用户已接受（目录不限制）**；日后可一步加目录白名单（§九 三个选项）|
| 无审计（看不到「谁在连」）| **探针保留**（`MCP_PROBE_ENABLED` 默认 1）；建议补 `request.client.host` |

> 想收紧时**不用返工**：§3.3 的 `TokenGuard` 已实测 11/11，加它约 25 行。

### 3.2 地址与监听策略：**默认零配置** ★

| 层 | 靠什么自动成立 | 需要配吗 |
|---|---|---|
| **监听**（服务绑在哪）| `--host 0.0.0.0` —— 哪台机器、哪块网卡都能连 | ❌ 不配 |
| **可访问性**（谁的 `Host` 被接受）| 动态枚举：环回 + 全部非环回 IP（psutil）+ **本机主机名/FQDN（含小写）** + `MCP_EXTRA_ALLOWED_HOSTS` 兜底 | ❌ 基本不配（**只在看到 421 时补一条**）|
| **产物链接里的地址** | **按请求 `Host` 推导**（§2.3）—— 主机用什么地址连，链接就是什么地址 | ❌ 不配 |

**需要配环境变量的唯一场景**：`MCP_PUBLIC_BASE_URL`（+ `MCP_PUBLIC_SCHEME=https`）—— ① 前面挂了**反代/端口映射**（对外地址 ≠ 本机地址）；② 需要 **https**；③ 以后做「异步任务结束后自动注册链接」时的**无上下文兜底**（§2.3 实测：`TaskRunner` worker 里没有请求上下文）。**本期 P3 不做 ⇒ 本期一个字都不用配。**

**主机侧建议**：用 **IP** 最稳（`http://192.168.0.58:50026/mcp`）；用主机名也可以（§2.3 已把它加进白名单）。**换远程机/换网段只改这一行，且改完必须新开会话**（MCP 配置无热重载）。

### 3.3 日后可选：服务端 Bearer（`TokenGuard`，原型已验 11/11 ★）

**做法**：在服务端加一个中间件，校验 HTTP 头 `Authorization: Bearer <MCP_ACCESS_TOKEN>`；**留空 = 不启用**（本机单机模式零变化）。覆盖面必须包含 `/mcp` **+** `/upload` **+** `/chat` **+** `/tools/list`（后三者连白名单都不管），豁免 `/health` / `/ready` / `/metrics`。

```python
_PROTECTED = ("/mcp", "/upload", "/chat", "/tools/list")      # 受保护
_EXEMPT    = ("/health", "/ready", "/metrics")                # 诊断豁免（探活/监控不带 token）

class TokenGuard(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        path = request.url.path.rstrip("/")
        if any(path == p or path.startswith(p + "/") for p in _PROTECTED) and path not in _EXEMPT:
            hdr = request.headers.get("authorization", "")
            if not hdr.lower().startswith("bearer ") or not secrets.compare_digest(
                    hdr.split(" ", 1)[1].strip(), settings.mcp_access_token):
                return JSONResponse({"error": "unauthorized", "error_code": "UNAUTHORIZED",
                                     "message": "缺少或错误的 Authorization 头",
                                     "hint": "do_not_retry"},
                                    status_code=401, headers={"WWW-Authenticate": "Bearer"})
        return await call_next(request)
```

| 实测项（`verif33.py`，11/11） | 结果 |
|---|---|
| `/mcp`：无 token / 错 token / 对 token | **401 / 401 / 200**（401 带 `WWW-Authenticate: Bearer` + `error_code=UNAUTHORIZED`）|
| `/tools/list`（原先完全不受保护）| 无 token **401**、有 token **200** |
| `/health`、`/ready`、`/metrics` | 无 token 也 **200**（豁免）|
| 真 MCP 客户端（带 token，走 LAN IP）| 调工具成功；**不带** token → 失败（客户端侧是 `ExceptionGroup`，排障要看服务端 401）|
| 绑 `0.0.0.0` 后本机 `127.0.0.1` | 仍 200 → **本机直连不受影响** |
| 中间件顺序 | `add_middleware` **后加的在最外层**（`TokenGuard` 后加 ⇒ 先执行）|

**客户端侧传 token（已实测）**：mcp SDK 用 `create_mcp_http_client(headers={"Authorization": "Bearer <token>"})`；Hermes 用 `hermes mcp add <name> --url <url> --auth header`（原生支持，token 存进 profile）。

**⚠️ 不要把 `/documents`、`/images` 纳入保护**：主机的浏览器/`curl`/下载器直接拉这些 URL，**带不了 `Authorization` 头**；它们靠不可猜 token + 短 TTL 自我鉴权（§九）。

**其它可选收紧**：`/chat`、`/upload` 非环回时直接 403（前提 6：远程不需要）；`fetch_artifact` 加「允许根目录」（§九）。

## 四、并发与排队

### 4.1 三种工具的队列与串行约束（实测）

| 队列 | 实现 | 容量 | 串行约束 | 状态机 |
|---|---|---|---|---|
| EDA 仿真 | `simulation.py` `_sim_tasks` + `_SIM_EXECUTOR(1)` | **在途**上限 8（计数 `QUEUED/ACCEPTED/RUNNING`，`>=8` → `SIMULATION_QUEUE_FULL`；不是"排队 8 个"）| 单 worker | QUEUED→ACCEPTED→RUNNING→SUCCEEDED/FAILED（+ TIMEOUT/REJECTED 等 proto 状态） |
| HFSS | `task_runner.py` `hfss_runner`（`max_tasks=50`、`max_run_seconds=7200`）| `max_tasks=50` | 单 worker + **`require_idle=True`（忙就拒）** | QUEUED→RUNNING→SUCCEEDED/FAILED |
| **CST** | `cst_runner`（默认 `max_tasks=50`、`ttl=7200`）| `max_tasks=50` | 单 worker，**不使用 `require_idle`（忙则排队，不拒）** ★ 实测订正：原稿「HFSS/CST 都用 `require_idle`」不成立 | QUEUED→RUNNING→SUCCEEDED/FAILED |
| turbocharts | `config.py` 信号量(1) | 串行 | 信号量 | 无任务状态（同步） |

**问题**：
1. **两套队列并存**（报告里的 C1 遗留项）——策略不一致（EDA 排队、HFSS `require_idle` 忙就拒绝）。
2. 队列策略对**多客户端**不公平（无优先级、无去重）。

**要求**：
1. 每个软件（AEDT/CST/ADS）各自串行（单实例约束），但**不同软件之间可并行**。
2. 多客户端提交时，队列**有界**（防止内存/任务无限堆积）、**有明确拒绝语义**。

**约束**：
- AEDT 是单实例桌面：同一时刻只能跑一个 HFSS 求解 → HFSS 队列必须串行且「忙则拒绝」。
- CST 是单实例：`run_solver` 与 `execute_vba` 不能并发 → CST 队列串行。
- ADS（EDI gRPC）有自己的队列上限。

**方案（阶段 1，单引擎机）**：

> 🔸 **2026-09-18 修订（实测复核后）**：**不再建议把两套队列合并成一套实现**——EDA 的"排队"与 HFSS 的"忙就拒"**恰好匹配各自的软件约束**（AEDT 单实例桌面 vs 批量导出），强行合并会把回归面引进主链路；**统一到"返回语义 + 错误码"即可**（`QUEUE_FULL` / `ANALYSIS_BUSY` / `hint`）。详见 §十三 P2 行。

1. **统一队列语义**（实现可暂不合）：三种工具各一个 `TaskRunner` 实例，语义统一为：
   - 提交返回 `task_id`；队列满 → `QUEUE_FULL`（`retry_safe`，客户端稍后重试）。
   - 单实例工具策略按软件分：**HFSS 用 `require_idle=True`**（忙 → `ANALYSIS_BUSY`）；**CST 不用 `require_idle`**（排队，见 §4.2 实测）。
2. **有界**：`max_tasks` 按工具设（HFSS/CST 小，EDA 中，避免内存膨胀）。
3. **公平**：默认 FIFO，够用；优先级（如「求解 > 导出」）作为后续增强，不首期做。

### 4.2 拒绝语义实测矩阵（2026-09-18，`edi_tmp/verif34.py` + `verif35.py`）

三种工具**三种策略**（这比"两套队列"更该先写清）：

| 工具 | 忙时提交第二个 | 队列满时 | 实测值 |
|---|---|---|---|
| **EDA**（`start_simulation_async`）| **排队**（单 worker FIFO）| **`SIMULATION_QUEUE_FULL`**（在途 ≥8 即拒）| 8 条在途 → `error_code=SIMULATION_QUEUE_FULL`，msg「当前已有 8 个仿真任务在进行或排队」|
| **HFSS**（`start_hfss_analysis_async`）| **`ANALYSIS_BUSY`**（`require_idle` 忙就拒，不排队）| **`TASK_LIMIT_REACHED`**（与"忙"**区分开**，码正确）| 忙 → `ANALYSIS_BUSY`；填满 50 条「已完成未过期」→ `TASK_LIMIT_REACHED`；空闲 → `success=True, status=QUEUED, hint=poll` |
| **CST**（`cst_solve_async` 等）| **排队**（**没用 `require_idle`**，第二个照样受理）| `max_tasks=50`（满了 `submit` 返回 `None`）| 忙时第二个提交仍返回 `task_id`；`servers/cst/` 内 `require_idle` 命中 = **0** |

**附带确认的 TaskRunner 细节**：① `require_idle` 在任务完成后**立即恢复**（`pending_count()==0`，条目仍在 TTL 内）；② 容量按**条目数**判满（`len(_tasks) >= max_tasks`，**含已完成未过期**）→ **R19 的「容量占用到 TTL」实测成立**；③ 单 worker → 排队任务串行执行，不会并发抢外部软件。

### 4.3 ⚠️ 同步工具会**冻结整个服务**（实测，2026-09-18）

**现象**：mcp 1.28 的 FastMCP 对**同步工具**是**直接调用**（源码 `func_metadata.call_fn_with_arg_validation`：`if fn_is_async: await fn(...) else: return fn(...)`，**没有 `to_thread`**）→ 工具跑在**事件循环线程**上，执行期间**整个服务停摆**：产物下载、`/health`/`/ready`/`/metrics`、**其它会话的 `get_*_status` 轮询**全部排队等待。

**实测（`edi_tmp/verif37.py` + `verif38.py` + `verif39.py`，用「每 200ms ping `/health`」捕捉冻结窗口）**：

| 场景 | 250ms 间隔 ping 的表现 |
|---|---|
| 空闲基线 | 样本 15 个，中位 **3ms**，最大 5ms，>200ms 的 **0** 个 |
| 同步探针 `sleep(8s)`（经 MCP 调用）| **只完成 2 个样本，单次 7846ms** —— 整段 8s 冻结；工具线程名 `Thread-1 (run)`（= 事件循环线程）|
| **真实工具 `turbocharts_convert`（子进程出图，1.6s）** | **单次 1344ms**（≈ 工具耗时）→ 期间下载/探活全停 |
| verif37 对照：同步工具运行中下载 5MB | **3ms → 1418ms（431×）** |

**为什么这条对远程特别要紧**：① 主机**下载产物**会被堵（正是本条需求）；② 主机**轮询任务状态**会被堵；③ 若某个同步工具跑 **>300s**，主机侧 MCP 客户端（Hermes 的 `read=300.0`）会**先超时断开**，而服务端还在跑（结果无人接收）；④ 同一主机开两个 agent 会话时互相拖死。

**受影响的主要是「同步慢工具」**：`turbocharts_convert`、`compare_simulation_results`、`generate_simulation_report`（16 步校验）、`cst_export_snp` / `cst_export_farfield`（内部 `cst_runner.run_sync`）、以及所有**走 gRPC 等待响应**的 EDA 工具（`call_grpc` 是阻塞调用：等待期间同样冻结）。**异步任务本身不受影响**（worker 在 `ThreadPoolExecutor` 里跑，不占循环）——所以「长任务用异步接口」这条纪律不只是建议，还是**避免冻结的唯一办法**。

**修法（三选一，推荐 a+c）**：

| 方案 | 做法 | 成本 |
|---|---|---|
| **a（推荐）** | 把慢同步工具改成 `async def`，内部 `await anyio.to_thread.run_sync(原同步实现, ...)` | 每个工具 ~3 行 |
| b（一次覆盖全部） | 给 `@mcp.tool()` 包一层「同步→线程」的装饰器，或在 `Tool.run` 上 monkeypatch 统一 offload | ~15 行，但**要回归 90 个工具**，且需确认 contextvar 传递 |
| c（配套） | 远程场景把「必须用异步接口」写进 docstring/客户端提示，不改代码 | 0 行，但不能根治 |

**修法已实测（`verif38.py` 的 C 组）**：同一实现用 `anyio.to_thread.run_sync` 包装后 →

| 实测项 | 结果 |
|---|---|
| 工具运行中的下载/探活 | **5ms → 12ms**（不再冻结）|
| 工具线程 | `AnyIO worker thread`（确认已脱离事件循环）|
| **§2.3 的 Host 推导是否还成立** | ✅ **`contextvar` 传得进线程**：`host_ctx='192.168.0.58:PORT'`、`base_in_thread=http://192.168.0.58:PORT` —— 修法与产物链接**不冲突** |

#### 4.3.1 配套要求：offload **必须同时加锁** ★（`verif40.py` A 组实测）

这些同步工具现在之所以"串行"，**靠的是它们占满事件循环这一副作用**——不是因为有锁。实测（读码 + 真调）：

| 证据 | 结果 |
|---|---|
| `servers/turbocharts/convert_raw.py` | **无 `Lock`/`Semaphore`、无 `run_sync` 串行**（读码）|
| **并发 2 个真实 `turbocharts_convert`**（offload 到线程后）| 2/2 都成功、各自出图 ✅，但**耗时 6.03s**（单个约 1.6s ⇒ ~3.7×，明显资源争用）|

⇒ **offload 的代价是「把原本被循环掩盖的并发冲突暴露出来」**。每改一个工具必须同时确认互斥：`cst_*` 走 `cst_runner.run_sync`（单 worker 串行 ✅ 已有）；`turbocharts_convert` / `compare_simulation_results` / `generate_simulation_report` **需要新加 per-tool 锁**（或并入 `TaskRunner`）。**只 offload 不加锁 = 从「冻结但正确」变成「不冻结但可能争用」**。

### 4.4 任务生命周期（统一状态机）

```
QUEUED → RUNNING → SUCCEEDED / FAILED
                    ↘ TIMEOUT（超过 max_run_seconds）
                    ↘ INTERRUPTED（引擎机重启，见 §七）
```

- 完成后保留 `ttl_seconds`（默认 2h）供客户端查询结果，过期清理。
- `max_run_seconds` 兜底：卡死任务标 `FAILED`，避免永久占用。

## 五、任务分发

### 5.1 单台远程机：进程内排队（现状，不改）

**问题**：任务在引擎机上由谁执行？多台引擎机时发给谁？

**现状**：单进程内 `ThreadPoolExecutor(1)` / 单 worker 线程。无跨进程/跨机。

**要求**：
- 单引擎机：任务按「工具」分到对应队列，各自串行。
- 多引擎机（未来）：能选一台空闲引擎机跑。

**约束**：
- 软件单实例 → 每台引擎机上同一软件只能一个任务在跑。
- 跨机分发意味着任务要能在任意引擎机上执行 → 依赖「软件 + 工程文件」都在那台机上。

**方案**：
- **阶段 1（单引擎机）**：本地线程池 + 工具队列，**不改**。这是「分发」的最小实现，已够用。
> ✅ **已拍板拓扑**：**一台主机可连多台远程机（引擎机）、每台远程机只归属一台主机** → ① 引擎机侧仍是「单机单客户端」，阶段 1 完全够用，「选一台空闲引擎机」的调度器**不需要**（阶段 2 维持「没到那步别做」）；② **哪台机器跑哪个引擎**由**客户端配置**决定（多地址并列/切换），引擎机之间互不感知、也不需要知道彼此存在。
- **阶段 2（多引擎机，才需要）**：引入调度器——一个外部队列（redis）+ 引擎机注册/心跳 + 「哪台引擎机空闲就发给谁」。**没到那步别做**。


### 5.2 同时使用多台远程机（多机并行）

**并行度从哪来**：**每台远程机自身** = 各软件之间可并行（ADS / HFSS / CST 各自串行）+ 同软件排队 + 有界队列；**跨机并行**靠主机把指令发到不同机器 ⇒ 总并行度 ≈ 机器数 × 每台能力。

**三个层级（按需要的自动化程度选）**：

| 层级 | 做法 | 开发量 | 适用 |
|---|---|---|---|
| **L1 多 server 并列**（**推荐起步**）| 主机侧 agent 配置里并列 N 个 server 条目（`eda-a`/`eda-b`/…），每台一个 URL。工具名会带 server 前缀，agent 能分辨目标机 | **0** | 1–3 台；由你/提示词指定目标机 |
| **L2 主机侧网关**（P5 可选）| 你机器上跑一个「MCP 聚合服务」：向上只暴露**一套**工具名（加 `target` 参数或自动选机），向下把 `tools/call` 转发给 N 台执行端；顺带做鉴权 / 日志 / 去重 / 优先级 | ~150–250 行 | ≥3 台；或想让 agent 不必关心机器名。**主要收益是控制上下文**（N×90 → 90 个工具）|
| **L3 中央调度器**（现在不做）| 中央队列 + 空闲探测 + 抢占 + 结果汇总 | 大 | 真到「一个链路拆到多台机并行跑」的规模再说 |

**L1 的配置示例（Hermes，0 开发即可用）**：

```yaml
mcp_servers:
  eda-hfss:                                   # 语义化命名 = 给 agent 的意图线索
    url: http://192.168.0.58:50026/mcp
    connect_timeout: 60
  eda-cst:
    url: http://192.168.0.77:50026/mcp
    connect_timeout: 60
```
（Claude Code 同理：`.mcp.json` 里并列两个 `type: http` 的 server。）改完**新开会话**生效。

**L1 的三条代价（必须有心理准备）**：
1. **上下文膨胀**：N 台 = N × 90 个工具 schema（3 台就是 270 个）→ 吃 context，也增加 agent 选错机器的概率。缓解：只配**当前要用的**机器；Hermes 侧可用工具集开关（`disabled_toolsets`）裁剪。
2. **命名即意图**：命名成 `eda-hfss` / `eda-cst` / `eda-lab2` 这种带语义的，agent 才不会乱挑。
3. **运维成本 ×N**：每台都要**手动启动**、**保持登录**（§18.5）；这是多机的真实成本。（白名单远程自动忽略，不再算一项）

**极端情况：一个任务想用多台机器**（例：20 通道链路拆开并行）
- 现状**没有任务拆分/汇总能力**：跨机编排只能由主机上的 agent 自己完成（它同时看得到多台的工具），或另写编排脚本；
- ⚠️ 硬约束 1：**主机看不到远程机的文件**，只能通过 `fetch_artifact` 下载产物 ⇒ 跨机汇总必须走「各自下载产物 → 主机侧合并」，**不能假设共享路径**（若坚持共享，需上 UNC 并改造工具的「会话目录」校验 —— 不建议）；
- ⚠️ 硬约束 2：**同一份 `.epp` / RAW 不能被两台机器的任务同时写**（服务端无工程级锁）；
- ✅ 产物取回不受影响：每台机器返回的下载 URL 按**各自请求的 Host** 推导，N 台的链接都能直接下载（§2.3）。

**与 P0.5 的关系（关键）**：想「一边在某台上跑仿真、一边盯状态或取产物」，**必须先做 §4.3 的 offload + 锁**；否则同步工具会把该机服务整段冻结，多任务并行的体验直接垮掉。

**推荐路线**：**L1（0 开发）先上** → 同时落 **P0.5** → 机器数 ≥3 或要「自动挑空闲机器」时再考虑 **L2 网关**。

## 六、状态存储与持久化

**问题**：任务状态存哪？引擎机重启后任务状态还在不在？

**现状**：**纯内存 dict**（`_sim_tasks`、`TaskRunner._tasks`），重启即丢：
- 运行中任务 → 状态消失，客户端轮询得 `TASK_NOT_FOUND`。
- 已提交未完成的任务 → 永久丢失。

**要求**：
1. 任务状态跨引擎机重启可恢复（至少能查到「这个 task 最终是成功还是失败」）。
2. 状态可跨重启查询（前提 2 下「多客户端共享」已非主因，理由回到「扛重启」，见 §11）。
3. 轮询接口（`get_*_status(task_id)`）签名不变。

**约束**：
- 单引擎机场景不需要分布式存储，sqlite 够用且零运维。
- 仿真结果（RAW 文件、日志）本身很大，**不塞进 DB**，DB 只存状态 + 结果文件的**路径**。

**方案（阶段 1）**：
- **sqlite 任务表**：
  ```
  tasks(task_id PK, tool, status, submitted_at, started_at, finished_at,
        result_path, error, metadata_json)
  ```
- `TaskRunner` / `_sim_tasks` 的读写从内存 dict 改为查表；`result` 大字段落文件、DB 存路径。
- **重启恢复**：启动时把「RUNNING / QUEUED」的任务标为 `INTERRUPTED`（worker 线程已随进程死，不可能继续），`SUCCEEDED/FAILED` 保留供查询。
- 客户端语义不变：`get_*_status` 查表，查不到 → `TASK_NOT_FOUND`。

> 注：这是把「内存状态」替换为「sqlite 状态」，是阶段 1 里工作量最大、收益最大的一项。

**表结构补强（建议）**：在 `tasks(...)` 基础上加 —— **`boot_id`**（每次启动生成、写入该次启动创建的任务行 → 重启后可区分"这行来自上一次启动"）、**`interrupt_reason`**（如 `service_restart`）、**`artifacts_json`**（**只在成功时写入**：`[{path, size, sha256}]`）、`params_hash`。写库用 `UPDATE ... WHERE task_id=? AND status IN (...)`（**幂等**，崩溃只会留下"最后已知状态"，不会写坏）；`PRAGMA journal_mode=WAL` + 单写者。

### 6.3 「重启 / 关机后会不会有脏数据？」—— 实测清单

**结论：不会有"数据库脏数据"（现在压根没有数据库），但会留下「状态黑洞 + 外部副作用」三类脏。** 逐年分层看：

| 层面 | 现状（实测） | 重启后 | 脏不脏 |
|---|---|---|---|
| **任务状态** | 纯内存（`_sim_tasks`、`TaskRunner._tasks`），全仓**无 sqlite/持久化** | **全丢**；旧 `task_id` 查 → **`TASK_NOT_FOUND` + `outcome_known=false`**，文案明确写「任务不存在、已经过期或服务已经重启」 | **不是脏，是空** —— 而且**不骗人**（`outcome_known=false` 就是给客户端"别当失败处理"的判据）|
| **任务痕迹** | ✅ **EDA（ADS 仿真）有日志**：`task=xxx status=QUEUED project=... timeout=600s` + 阶段行（`phase=SUBSCRIBED` → `ACCEPTED code=0` → `COMPLETED status=SUCCEEDED duration=0.1s`）；路径 `%TEMP%\edi\data\log\edi_mcp_YYYYMM.log`（按月、10MB×5 轮转，当前 2.3MB/3.6 万行）<br>❌ **HFSS / CST 任务零日志**（`task_runner.py` 里没有任何 `logger.` 调用）| EDA 任务**可从日志追溯**；HFSS/CST **完全无痕** | EDA 可救；**HFSS/CST 是黑洞** ← 建议补日志（十行级）|
| **外部副作用** | ① `subprocess.Popen([ansysedt.exe, ...])` **没有 kill / terminate / wait 绑定**（grep 无命中）→ 服务被杀时 **AEDT/CST 可能继续跑**<br>② `*.aedt.lock` 残留<br>③ 半成品 RAW/PNG/CSV（**没有"完成才登记"机制**）<br>④ 启动时**无任何自检**（不扫锁、不扫孤儿进程、不报告残留任务）| 孤儿进程可能仍占着软件/锁；半成品文件可能被误当结果；锁**通常能自愈**（死 PID → 下次 `open_*` 自动清理，§七 实测）| ← **"脏"主要在这里** |

**分级处置（从便宜到贵）**：

| 档 | 动作 | 成本 | 收益 |
|---|---|---|---|
| **A. 立刻（十行级，建议并入 P0.5）** | ① **HFSS/CST 补任务日志**（提交/开始/结束各一行，格式照 EDA）；② **启动自检**（只报告不动作）：扫 `*.aedt.lock` + 孤儿 `ansysedt.exe`/CST 进程 + 打印"上次可能有任务被中断"，顺手对死 PID 锁复跑一次 `cleanup_stale_project_lock` | 低 | 追溯能力补齐 + 重启后一眼看出要不要人工清理 |
| **B. 操作纪律（0 代码）** | 重启/关机前先 `list_eda_tasks()` + `get_hfss_analysis_status()` 确认没有在跑的；重启后先看**任务管理器有无 `ansysedt.exe`/CST 残留**、输出目录时间戳、`.aedt.lock`；Windows 重启后**记得重开 EDI 客户端**（否则 50055 不通 → 所有 EDA 工具报错，这最容易"看起来像脏数据"）| 0 | 现在就能用 |
| **C. P1（sqlite，方案内）** | 任务落库 + 启动时把非终态标 **`INTERRUPTED`**（**不是 FAILED**）+ `list_tasks(status="INTERRUPTED")` 供客户端发现 + **产物登记（成功才写 path/size/sha256）** | 中 | 跨重启可查；半成品天然不登记 |
| **D. 明确不做** | **不自动重跑被中断的任务**（外部副作用未知：可能已跑完、可能占着软件）→ 由人或客户端决定；`outcome_known=false` 就是给这个判断用的 | —— | 避免"自动重跑制造脏数据" |

## 七、故障恢复

**问题**：引擎机重启 / 崩溃 / 软件卡死时，怎么收场？

**现状**：
- 引擎机重启 → 内存任务全丢（§六）。
- 软件卡死 → `max_run_seconds` 兜底标 FAILED（TaskRunner 已有；但注意其「不删条目、槽位占用到 TTL」的缺陷见报告 R19）。

**要求**：
1. 重启后：`RUNNING`/`QUEUED` → `INTERRUPTED`；已完成任务保留。
2. 崩溃遗留的**软件锁文件**要能清理（AEDT 有 `.aedt.lock`，见 `cleanup_stale_project_lock`）。

**约束**：
- 软件进程（`ansysedt.exe`）可能在引擎机重启后仍存活/或留下锁，需有兜底清理。

**方案**：
- 重启恢复：随 §六 sqlite 一起做（标 INTERRUPTED）。
- 锁清理：复用现有 `cleanup_stale_project_lock`（PID 存活时不删），远程场景引擎机自己管理锁，客户端不管。
- 卡死兜底：修 R19（`max_run_seconds` 标 FAILED 时**真正释放容量**，改成只数未结束任务）。
- **MCP 服务启动方式：本期 = 手动启动**（2026-09-18 用户确认，**不做自启动**）：
  - 启动：登录到远程机 → 跑 `python start_servers.py --transport streamable-http --host 0.0.0.0`（现场版 = 对应 exe）→ `curl http://127.0.0.1:50026/ready` 确认。
  - ⚠️ **唯一仍要守的前提**：服务进程所在的**用户会话必须常驻** —— **别注销、别让机器睡眠/关机**（§〇 前提 3）。**注销会直接杀掉服务与它拉起的软件**；锁屏是否影响 AEDT 的 COM 附着**未实测**（真遇到 AEDT 相关异常时，先怀疑"是不是锁屏/休眠了"）。
  - 🔸 **自启动（留待以后，不在本期）**：真要做时用 `schtasks /create /tn edi-mcp /sc onlogon /rl highest /f /tr "\"<python.exe 或 exe 绝对路径>\" \"<start_servers.py 绝对路径>\" --transport streamable-http --host 0.0.0.0"`（`start_servers.py` **不是可执行文件**，`/tr` 必须写 python/exe 绝对路径）。⚠️ **不要**用 `/sc onstart` 默认账户（SYSTEM）或注册成 Windows 服务（NSSM）——那是 **Session 0（无交互桌面）**，纯 HTTP 服务没事，但**它拉起的 AEDT（COM）/CST 很可能起不来**（未实测，属风险提示）；配套还要设自动登录 + 不锁屏 + 不睡眠。

> ✅ **锁清理 4 分支实测（2026-09-18，`edi_tmp/verif34.py`）**：无锁 → no-op；**死 PID → 删（`stale_lock_removed`）**；**活跃 AEDT PID → 保留（`lock_active`）**；坏格式：AEDT 不在跑 → 删、**AEDT 在跑 → 保守保留（`lock_unknown_format`）**。调用点 = `open_hfss_project`（`servers/ansys/project_manage.py:92`）与 `close_hfss_project`（`:244`/`:297`）→ **「复用现有清理」成立**（不是死代码）。
> ⚠️ **同时复测确认 R12**：`get_project_lock_path` 用 `Path(...).with_suffix(".aedt.lock")` → `demo.aedtz` 与 `demo.aedt` 得到**同一把锁** `demo.aedt.lock`（`.aedtz` 后缀被截断）→ 同目录同名工程会**互相踩锁**；属未修项（`docs/审查报告.md` R12，1 行可修）。
> ℹ️ 当前 `ansysedt` 未运行（`get_aedt_pids() = []`）→ 现网无活跃锁。

**建议的启动自检（P0.5 档 A，只报告不动作）**：服务启动时做 3 件事并在日志里打一行摘要 ——
1. **孤儿进程**：`psutil` 列 `ansysedt.exe` / CST 进程；若存在但本次启动没有任何 RUNNING 任务 → 打 WARN（提示"可能是上次遗留，占着软件或锁"）；
2. **残留锁**：扫工作区 `*.aedt.lock`，对**死 PID** 的复跑 `cleanup_stale_project_lock`（活跃 PID 保留 —— 行为与 `open_hfss_project` 一致）；
3. **中断提示**：提示"上次启动可能有任务被中断，请查 `%TEMP%\edi\data\log\edi_mcp_*.log`"（P1 落库后改为直接列出 `INTERRUPTED` 任务）。

## 八、路径与文件语义

**问题**：客户端传的路径是「引擎机路径」还是「客户端本地路径」？

**现状**：所有工具用绝对路径，读写都在**引擎机**（`ProjectReader`、`capture_schematic`、gRPC 都假定本机文件）。

**要求**：客户端必须传**引擎机上的路径**（如 `D:\EDI-Workspace\xxx.epp`）。

**约束**：客户端本地路径对引擎机无意义；引擎机路径对客户端本地无意义。

**方案**：
- 不改成「路径映射」（太复杂且易错）。
- **约定写进客户端提示词 / README**：远程场景所有路径都是引擎机路径。
- **远程客户端必须先 `list_epp_projects(folder_path="引擎机目录")`** 列出引擎机上的工程，再从中选路径——`validate_file` 一类校验**都在引擎机执行**，客户端本地"看起来存在"的路径一律无效，别让 agent 凭记忆猜路径。
**边界（已拍板 2026-09-18）**：**不做路径白名单**——远程客户端可以传引擎机上任意可访问路径（含 `C:\` 根目录、`.env`）。所以路径安全的**唯一边界就是 §三 的鉴权**：连得上的人才能指定路径。这也是 §三 的 token 必须做的直接原因。

## 九、产物传输（图片 / 报告 / RAW）

**问题**：仿真结果、截图、报告都生成在引擎机，客户端怎么拿到？

**现状**：
| 产物 | 现状 | 远程可用？ |
|---|---|---|
| `show_image` ≤10MB | base64 内嵌 `ImageContent` | ✅ 直接可用 |
| `show_image` >10MB | 返回引擎机本地路径 | ❌ 客户端读不到 |
| `open_document` link | 生成 `/documents/{token}` HTTP 链接 | ⚠️ 链接指向 127.0.0.1（#2 问题） |
| `capture_schematic` 截图 | 生成文件 + 返回路径 | ❌ 路径在引擎机 |
| **产物链接 `file_uri` / `markdown_link`** | `build_file_link()`——**4 个工具**：`capture_schematic`、`generate_simulation_report`、`compare_simulation_results`、`turbocharts_convert` | ❌ **更糟**：`file://` URI 指向**客户端本机**，agent/用户点开会失败或打开错文件 |
| **`.snp` / `.raw` / 任意非办公产物**（如 `cst_export_snp` 的 `snp_path`）| `open_document` 的扩展名白名单**只有 10 种办公格式**（`.pdf/.doc(x)/.xls(x)/.ppt(x)/.txt/.csv/.rtf`）→ **实测 `.s2p`/`.raw` 一律 `UNSUPPORTED_FORMAT`**；`cst_export_snp` 更只回一个 `snp_path` | ❌ **完全拿不到**（用户明确点名的场景）|

**要求**：远程客户端能拿到产物文件本身，而不是只有引擎机路径。

**约束**：
- 产物文件在引擎机，客户端没有文件系统访问权。
- 大文件不能靠 MCP 文本返回（会撑爆上下文）。

**方案（⭐ 主方案已实测 11/11，`edi_tmp/verif36.py`）**：

**0. 新增「远程专用工具」`fetch_artifact(file_path, ttl_seconds=600)`** —— 一次解决**所有**产物类型：

```python
@mcp.tool()
def fetch_artifact(file_path: str, ttl_seconds: int = 600) -> dict:
    """把引擎机上的产物注册成可下载 URL（仿真结果/SNP/RAW/图/报告/任意文件）。"""
    p = Path(file_path).expanduser().resolve()
    if not p.is_file():
        return {"success": False, "error_code": "FILE_NOT_FOUND", "message": f"文件不存在: {p}"}
    ttl = max(30, min(int(ttl_seconds), 3600))
    # ⚠️ 勿 _doc_store._ttl = ttl（会污染 open_document 的全局 TTL）；改为 register 支持 per-token ttl
    token, url = _doc_store.register(str(p), disposition="attachment", ttl=ttl)
    return {"success": True, "url": url, "file_name": p.name, "size_bytes": p.stat().st_size,
            "sha256": _sha256_file(p), "expires_in": ttl}   # 大文件分块哈希，勿 read_bytes 全量
```

> ⚠️ **两处需配套实现（本片段是示意，非现成代码；`servers/token_registry.py` 已核实）**：
> ① **`TokenStore.register` 必须加 `ttl` 形参**——现在的签名是 `register(self, path, **extra)`，`expires_at` 恒为 `time.time() + self._ttl`（第 40 行）⇒ **直接写 `register(..., ttl=ttl)` 只会把 `ttl` 塞进 `**extra` 当垃圾字段、完全不生效**；而退回「`_doc_store._ttl = ttl`」会**永久污染 `open_document` 的全局默认 TTL**（同一个 store 实例）。最小改法：
> ```python
> def register(self, path: str, ttl: int | None = None, **extra: Any) -> tuple[str, str]:
>     ...
>     "expires_at": time.time() + (ttl if ttl is not None else self._ttl),   # ← 只改这一行
> ```
> ② **`_sha256_file(p)` 分块哈希**（手写 `for chunk in iter(lambda: f.read(1 << 20), b""): h.update(chunk)`）—— 注意 **`hashlib.file_digest` 不能用**：它是 **3.11+** API，而本仓 `requires-python = ">=3.10"`，现场 Win7 打包用 `.venv-win7` 的更低版本，**必须用手写分块循环**；顺带避免几百 MB 的 RAW 被 `read_bytes()` 全量读进内存。
> **实测坐实（`edi_tmp`，2026-09-18）**：`register(path, ttl=1800)` → token 字典 `{'expires_at': …, 'disposition': 'attachment', 'ttl': 1800}`，**实际剩余仍 600s**（传参只当垃圾字段）；`_doc_store._ttl = 1800` → 之后**任何**注册（含 `open_document`）都变 1800s（**全局污染**）。两种写法都不能用，必须改 `register` 签名。
> ③ **测试缺口**：`tests/` 里**没有任何 token 相关测试** → 改 `register` 时**必须补 1 条单测**（断言「per-token `ttl` 生效」且「不影响 `open_document` 的默认 600s」），否则现有 415 条套件**覆盖不到**这次改动。

**关键点：不校验扩展名**（只校验文件存在），**复用既有 `/documents/{token}` 路由与 store** —— **零新增路由、零新增存储**；URL 里的 host 由 §2.3 的**请求 `Host` 推导**给出。

| 实测样本（经非环回 Host 调用 → HTTP GET） | 结果 |
|---|---|
| **`.s2p`（Touchstone）** / `.raw`（ADS 结果）| **200，字节 + sha256 与源文件一致** |
| PNG / **含 NUL 的二进制** | 同上，逐字节一致（不做文本处理）|
| **中文文件名**（`仿真结果_通道1.s2p`）| 200 且 `Content-Disposition: attachment; filename*=utf-8''…`（RFC5987，**头合法**）|
| **5 MB 大文件** | 200，5,242,880 B 一致（HTTP 直下，**不经 MCP 上下文**）|
| 文件不存在 | `FILE_NOT_FOUND`（不是空文件）|
| 伪造 token | **404**（不可枚举）|

⚠️ **安全边界提示：`fetch_artifact` 是「远程机任意文件读取」通道**（`verif40.py` E 组实测：`C:/Windows/win.ini` → **200，92 B**）。配合「本期不做鉴权」⇒ **任何能连到远程机的人都能下载远程机上任意文件**（含 `.env`、SSH 私钥、他人工程）。

**三个可选收紧（待你定，成本都低）**：

| 方案 | 做法 | 代价 |
|---|---|---|
| A | 加「允许根目录」配置（默认 = 工作区/工程目录；留空 = 任意）| 跨目录取文件要改配置 |
| B | 只允许取「本进程已产出/登记过的文件」| 实现复杂，工程文件动过就取不到 |
| **C ✅ 已定（2026-09-18 用户决定）** | **不限制目录**（接受现状）| **内网无鉴权 ⇒ 任意文件可下载**（用户明确接受；见 §十四 风险 16）|

> 与「路径任意接受」口径**不冲突**：那条是对**工具入参**；`fetch_artifact` 是**新增的外泄面**，尺度可以不同。

**为什么不选「把 `.snp/.raw` 加进 `open_document` 的扩展名白名单」**：① 白名单永远不全（下一个产物格式又得改一次）；② 它与已拍板口径「**任意可访问路径都接受**」（§〇 前提 4）直接矛盾；③ `open_document` 是**文档**语义、白名单本身是信任边界（§九「明确不动」）。**新增一个专职工具更干净**，也正是「远程专用工具集」的第一件。

**1. `MCP_PUBLIC_BASE_URL`**（§三改动 2）让 token 链接指向引擎机对外地址 → `open_document`/`show_image` 大图的链接远程可点开/下载。
2. **`show_image` >10MB 改为也注册 token 链接**（现在只内嵌 ≤10MB），远程用 HTTP 拉取。**成本极小（≈3 行）**：`TokenStore(route="/images")` 与 `/images/{token}` 路由**都已存在**，照着 `open_document` 的写法调 `_image_store.register(path)` 即可 → 建议**提前到 P0.5**（"远程拿不到产物"是最立刻可感的挫败点）。
3. 报告下载走 `open_document(mode="link", disposition="attachment")`。
4. **`file://` 链接（上表末行）**：远程场景把 `build_file_link` 的返回改成 token 链接（同样复用 `TokenStore` + `/documents`），或至少在返回值/docstring 里标注"该 `file://` URI 仅在引擎机有效"——否则 agent 会以为"文件已生成、可以打开"。
5. **可选增强**：让**产物类工具自动带链接**——`build_artifact()` 里补 `url` 字段、`cst_export_snp` 补 `artifacts`+`url`（各 ~3–5 行），这样 agent 一拿到结果就有可下载地址，不必再调 `fetch_artifact`。

⚠️ **产物通道的鉴权方式（有意如此）**：`/documents/{token}`、`/images/{token}` **不在 Bearer `TokenGuard` 的保护清单里** —— 它们靠**不可猜 token**（`secrets.token_urlsafe(24)`）+ **短 TTL** 自我鉴权。这是**刻意设计**：主机的浏览器/`curl`/下载器直接拉这个 URL，**带不了 MCP 的 `Authorization` 头**；若把这俩纳入 Bearer 保护，产物就下载不了。

## 十、错误处理与可观测性

**问题**：远程多客户端出问题时，怎么定位？

**要求**：
1. 每个任务有唯一 `task_id`，日志带 `task_id` 关联。
2. 引擎机有集中日志 + 指标（当前已有 `/metrics`、`get_service_logs`、`/health`、`/ready`）。

**约束**：远程客户端看不到引擎机 stdout，必须靠服务端日志 + 结构化返回。

**方案**：
- 现有 `/metrics`（任务数、调用次数/失败/耗时）、`get_service_logs`、`/ready` 已覆盖大部分，远程通过 HTTP 可访问。
- 补充：任务日志（`ads_output`）已随 `get_simulation_async_result` 返回，HFSS/CST 的进度走 `get_*_status` 的 `message`。
- 错误码统一（已有 `error_response` + `hint`），客户端按码分支。

**⚠️ 无鉴权下的可观测性（2026-09-18 决策后新增）**：

| 项 | 说明 |
|---|---|
| **审计线索** | 远程＝无鉴权 ⇒ **`ProcessProbeMiddleware` 必须保留**（它打印来源进程）——**这是唯一的「谁在连」线索**。原稿建议「默认关掉省开销」**已改**（§〇 前提 8 / 附录 A.1）。⚠️ 远程连接反查不到进程，日志里 `exe=`/`cmd=` 会是空，**建议在探针里补一行 `request.client.host`**（来源 IP），否则只剩「有人连过」这个信息。|
| **`/metrics` 匿名可达** | 无鉴权下任何人可拉指标（调用次数/失败数/耗时）。**不要**往 `/metrics` 里塞项目名、路径等敏感信息。|
| **`421 Invalid Host header` 是「配置问题」信号** | 出现 421 不用查网络——是**客户端的 `Host` 不在远程机白名单**：① 把该 IP/主机名加进 `MCP_EXTRA_ALLOWED_HOSTS`；② 或检查枚举是否漏了网卡/主机名（§2.2）。|

**远程排障三步（建议写进操作手册）**：
1. `curl http://<远程机>:50026/ready` → 看 `tool_count` / `tools_hash`（服务活着、工具加载完整）；
2. 调一个**只读工具**（如 `get_service_status`）→ 链路通不通；
3. 分流：**421** → 补白名单；**连接失败** → 服务没起 / 防火墙 / 地址错；**报 `EDI_*`/`CST_*`** → 是**远程机本地**的 EDA 问题（与远程链路无关）。

## 十一、多客户端协调

**问题**：多个客户端同时操作同一台引擎机，怎么不互相踩？

**要求**：
1. 状态共享（所有客户端看到同一份任务状态）。
2. 幂等/去重：同一请求别重复提交（同项目同参数）。
3. 公平：一个客户端别饿死其他客户端。

**约束**：
- 无状态 HTTP + 多客户端 → 服务端必须用**共享的持久状态**（sqlite），不能靠客户端内存。
- 软件单实例 → 冲突不可避免，只能排队。

**方案**：
- 状态共享：§六 sqlite 解决。✅ **已实测（2026-09-18）**：`stateless_http=True` 下**两个客户端并发调用互不串扰**（各自 `Host`、参数都正确；`edi_tmp/verif32.py`）——「无状态 HTTP 天然支持多客户端」这个前提至此有实测支撑；同进程内的内存态任务表本就共享，跨引擎机重启的持久化才需要 sqlite。
- 去重：服务端按「工具 + 参数指纹」做**短窗口去重**，防重复提交。⚠️ **三点必须写清，否则会误伤**：
  1. **别用"工具+参数指纹"做长窗口去重**——改完工程磁盘内容、参数没变再跑同一仿真，指纹完全相同，会被当成重复请求而**静默吞掉合法重跑**；
  2. 命中重复时**返回既有 `task_id`**（幂等语义），而不是返回错误/拒绝；
  3. 指纹里纳入 `project_path` 的 **mtime/大小**，或只做**极短窗口（如 10s）**去重。
  ⚠️ **`chat` 的 `_is_duplicate_tool_call`（`servers/chat/service.py:867`）不能直接搬**：它是「同一轮多轮对话内」的调用去重，与本层"防多客户端重复提交任务"语义不同。

> 🔸 **2026-09-18 按拍板前提 2 降级**：引擎机**只归属一台主机** → 服务端**不存在多客户端竞争**，本节的 **「去重」「公平/优先级」降为延后项**（不是不做，是不必现在做）。仍然实用的是：① 同一主机上可能**同时开多个 agent 会话**（如 Hermes + Claude Code）→ 状态共享靠同进程内存态 + §六 sqlite 即可；② 多会话并发受既有的 `_EDA_LOCK`/单 worker **串行保护**，无需新增机制。
- 公平：默认 FIFO；跨客户端优先级不首期做。⚠️ 但要把**症状**写清：FIFO 下**一个 2 小时的 HFSS 求解会挡住同引擎机的全部短任务**（导出/截图/turbocharts），多客户端时这是最容易被投诉的点——现有"按工具族分队列"通常已够，不必上优先级。

## 十二、兼容与迁移

**要求**：
1. 现有「本机单机」模式不受影响（默认行为不变）。
2. 现有工具签名、`task_id` 轮询接口不变。

**约束**：
- 大量客户端/脚本已依赖现有返回结构，破坏性变更要避免。

**方案**：
- `--host` 默认 `127.0.0.1`（本机模式零变化）；`MCP_PUBLIC_BASE_URL` 留空时 `get_server_base_url` 行为不变；**`transport_security` 只在 host 非环回时才覆盖**（环回时保持 SDK 默认）→ 本机模式同样零变化。
- sqlite 持久化是「底层替换」，上层 `get_*_status` 接口不变。
- 统一队列（§四）要注意 `task_id` 格式和状态机兼容（EDA 的 proto 状态 vs TaskRunner 状态），迁移时保留别名/映射。

**新增配置项清单（全部可选，留空 = 保持现状）**：

| 环境变量 | 默认 | 作用 | 不配的后果 | 实施状态 |
|---|---|---|---|---|
| `MCP_BIND_HOST`（或 `--host`）| `127.0.0.1` | 监听地址；远程填 `0.0.0.0` | 保持只监听本机（**默认零变化**）| ✅ **已落地** |
| `MCP_EXTRA_ALLOWED_HOSTS` | 空 | 手工补 `allowed_hosts`（逗号分隔，IP 或主机名）| 只影响没被自动枚举到的地址（**看到 421 才需要补**）| ✅ **已落地** |
| `MCP_PUBLIC_BASE_URL` | 空 | 产物链接的**覆盖**地址（反代/端口映射/https/无请求上下文兜底）| 正常不需要（链接按请求 `Host` 推导）；**挂反代才必须配** | ⛔ **未加**（本期未落）|
| `MCP_PUBLIC_SCHEME` | `http` | 产物链接协议（填 `https`）| 走 https 反代时链接会写成 `http://` | ⛔ **未加**（本期未落）|
| `MCP_PROBE_ENABLED`（建议）| `1`（开）| 白名单留空时的探针中间件开关 | 关掉 = 失去唯一审计线索（**不建议关**）| ✅ **已落地**（实测关掉 → 打印 `Guard: disabled`）|

> ⛔ 的两个变量**不影响本期「连得上 + 拿得回产物」**：不挂反代、不走 https 时，链接按请求 `Host` 推导已经正确；**只有**「异步任务里注册产物链接」这一条会回落成 `127.0.0.1`（见 §2.3 末的实测）。要上反代/https，或要做 P0.5 的异步产物，就必须先补这两个变量。

**「本机单机模式零变化」逐项核对**：
1. `MCP_BIND_HOST` 默认 `127.0.0.1` → 启动行为与现在一致；
2. 环回 host 时**不覆盖** `transport_security`（保持 SDK 默认）→ 本机客户端行为不变；
3. `get_server_base_url()` 的回落路径与现在一致（含 `0.0.0.0`→`127.0.0.1` 的映射）—— ✅ **实测**：`tests/test_utils.py` 既有断言（`set_server_address("0.0.0.0", 9000)` → `http://127.0.0.1:9000`）**未改即过**；`MCP_PUBLIC_BASE_URL`/`_SCHEME` 本期**未实现**，故不参与；
4. `MCP_EXTRA_ALLOWED_HOSTS` 空 → 不参与 ✅；
5. 本期**不加任何鉴权中间件** ⇒ 本机调用链上**只多一个 `RequestBaseURLMiddleware`**（读一个 header、命中允许列表才写 contextvar）—— ✅ **实测**：不带参数启动的 banner 三行与旧版**逐字一致**、`/ready` 的 `allowed_hosts=3`（= SDK 默认环回）。

## 十五、总结

**远程多任务 = 四件事**：
1. **远程可用**（P0，**7 项**）：`--host 0.0.0.0` + **`transport_security` 动态枚举**（含**主机名/FQDN**，§2.2）+ **public URL 按请求 `Host` 推导**（§2.3）+ 白名单远程自动忽略/**探针保留** + **`fetch_artifact`**（产物取回，§九）+ **Host 校验** + **`MCP_PUBLIC_BASE_URL` 兜底**。**地址零配置**（§2.3）。
2. **鉴权本期不做**（前提 8）：**直接访问、内网可信** ⇒ 远程无鉴权开放；`TokenGuard` 原型已备好（§3.3，11/11），后面想加随时可加。
3. **并发不冻结 / 有序**（P0.5 + P2）：**先把慢同步工具 offload 出事件循环并配套加锁**（§4.3 —— 不做则下载与轮询被冻结；只 offload 不加锁则并发争用）；再谈队列语义，**统一的是「语义」不是「实现」**（`QUEUE_FULL`/`ANALYSIS_BUSY`，两套队列各自保留）。
4. **状态可靠**（P1）：sqlite 持久化 + 重启恢复 —— 拓扑确定后理由回到「扛重启」，「多客户端共享」已非主因。

AEDT/CST/ADS 的「单实例」本质决定了这是**串行调度**问题，不是并行计算问题——统一队列 + sqlite 就足够，分布式调度是假需求。拍板拓扑之后这一点更明确：**一台主机可连多台远程机、每台远程机只归属一台主机**，「多引擎机」由客户端侧配多地址解决，服务端不需要调度器、也不需要知道其它引擎机的存在。

## 十七、客户端侧（主机）接入要点（2026-09-18 补，原缺）

> 本节说的「客户端」= **主机上跑的 agent**；它连的每一台目标都是**远程机（引擎机）**。

### 17.0 客户端形态：**远程必须用 HTTP**（主机侧不启动任何服务）★

**结论：远程场景只需要启动「远程机上那一台 MCP 服务」**。主机上跑的是 **MCP 客户端**（Hermes / Claude Code 自带的那部分），它**不起服务、不监听端口**，只往远程机的 `/mcp` 发 HTTP 请求。

| 形态 | 谁跑 MCP 服务 | 客户端怎么配 | 适用 |
|---|---|---|---|
| **A. HTTP**（**远程正解**）| **只在远程机**：手动启动 `start_servers.py --transport streamable-http --host 0.0.0.0` | agent 配 `url = http://<远程机IP或主机名>:50026/mcp` | ✅ 远程 |
| **B. stdio**（本机模式）| **由客户端自己 spawn 在「客户端本机」** | `.mcp.json` 形如 `"command": "uv", "args": [..., "start_servers.py", "--transport", "stdio"]` | 只在**软件与本机同一台**时成立 |
| ~~两侧都启动~~ | —— | —— | ❌ **不要**：主机上起的服务够不着远程机的 COM/AEDT（还会去连**本机** `50055` gRPC），纯属白起、且会误导排障 |

**两台客户端的现状核对（本机实测）**：

| 客户端 | 当前配置 | 远程要怎么改 |
|---|---|---|
| **Hermes** | `mcp_servers.eda.url = http://127.0.0.1:50026/mcp`（**已是 HTTP**）| 只把 URL 换成 `http://<远程机>:50026/mcp` + **新开会话** |
| **Claude Code** | 仓库 `.mcp.json` 是 **stdio**：`uv --directory D:/GitLabCode/edi-grpc-mcp run python start_servers.py --transport stdio`，并把 `EDA_GRPC_SERVER=127.0.0.1:50055` | ⚠️ **必须改成 HTTP 类型**（`url` 指向远程机），否则它**spawn 的是本机服务**、连的是**本机 EDI**；具体字段名以客户端版本文档为准，**改完新开会话** |

> 推论（与 §2.4 呼应）：远程机上的服务在 `--host 0.0.0.0` 下**自动忽略白名单**（无需手动 `MCP_ALLOWED_PROCESSES=`），因为主机的 HTTP 请求反查不到来源进程。而 stdio 形态之所以"绕开白名单"，正是因为服务是被客户端**本机 spawn** 的。

| 项 | 要点 |
|---|---|
| **URL** | `http://<引擎机IP或主机名>:50026/mcp`（**必须带 `/mcp`**；根路径 `/` 是 Web UI，不是 MCP 端点）|
| **多台远程机怎么配** | 见 **§5.2**（L1 多 server 并列 / L2 主机侧网关 / L3 调度器）。拍板拓扑是「**一台主机可连多台远程机**」，两种做法：① **并列多个 server 条目**（如 `eda-a`、`eda-b`，工具前缀不同、可同时用，但工具表变长）；② **同一 server 改 URL 切换**（干净，但 ⚠️ **MCP 配置无热重载，改后必须新开会话**）。建议：常用的一台常熟，其它的按需切 |

| **启动软件** | `launch_edi` / `launch_aedt` / `open_hfss_project` 都是**在远程机上启动软件**的动作——**主机侧不需要装 EDA**，也不要假设本机有什么（§一 原则）|
| **路径语义** | 一切路径都是**引擎机（远程机）路径**；先 `list_epp_projects(folder_path=引擎机目录)` 列工程再选，别猜 |
| **产物获取** | ① 调 **`fetch_artifact(path)`** 拿 URL（返回 `size_bytes`/`sha256`/`expires_in`）→ **直接 HTTP GET 下载**（支持 `.snp`/`.raw`/PNG/二进制/中文名/大文件）；② 图片 ≤10MB 仍可 `show_image` 内嵌；③ `open_document(mode="link")` 适合办公文档；④ **不要用 `file://` URI**（指向主机本机，必失败）。⚠️ 链接**默认 10 分钟有效**，长任务请在**取用时**再注册，或重调 `fetch_artifact` 续期 |
| **长任务** | 只用异步接口：`start_*` → 轮询 `get_*_status(task_id)` → `get_*_result`；**远程别用同步仿真工具**（无 `task_id`，超时后结果无处可查）|
| **超时设置** | 放宽客户端 connect/read 超时：服务端单 worker 串行 + 有界队列，长任务动辄分钟级 |
| **Hermes / Claude Code 配置** | `mcp_servers.<name>.url = http://<引擎机IP>:50026/mcp`；⚠️ **MCP 配置无热重载，改 URL 后必须新开会话** |
| **断线重连** | 任务状态在引擎机侧（用 `task_id` 查），客户端重连后用同一 `task_id` 继续轮询；P1（sqlite）落地后引擎机重启也还能查到终态 |
| **并发** | 不同软件（ADS/HFSS/CST）可并行，同一软件串行；同一工程不要两客户端同时改（无工程级锁）|

## 十九、异常与边界情况清单（全链路）

> 链路：**主机 agent（MCP 客户端）** → HTTP → **远程机 MCP 服务** → ├─ 本机 **COM** → AEDT/HFSS　├─ 本机 **官方 API** → CST　└─ **gRPC** → EDI/ADS
> 下表逐层穷举异常与边界。**「实测」= 本方案跑过的证据**；「需补」= 目前没有保障、建议补的动作。

### 19.1 链路与连接层

| # | 场景 | 现在的行为 | 客户端看到 | 处置 |
|---|---|---|---|---|
| 1 | 服务没启动 / 网络不通 / IP 变了 | TCP 连不上 | 连接失败/超时 | 先 `curl http://<IP>:50026/ready`；查服务是否在跑、地址是否变（§3.2）。**排障新增字段**：`bind_host`（实际监听地址）+ `allowed_hosts`（生效的 Host 条数；若为 `3` 说明还在 SDK 默认环回模式 → 服务是旧版或没传 `--host`）|
| 2 | 客户端用了**自动枚举不到**的 `Host`（反代域名 / 另一个网段 / 另一台机的中转）| **HTTP 421 `Invalid Host header`** | MCP 握手失败（ExceptionGroup）| 先看 `/ready` 的 `bind_host`/`allowed_hosts` 是否正常；加 `MCP_EXTRA_ALLOWED_HOSTS`（§2.2）。**✅ 已修**：LAN IP、主机名（含大小写）、非环回 IPv6 现在都自动在允许列表内（实测 200）—— 原来的「换 IP/主机名就 421」不再出现 |

| 4 | 下载产物中途断网 | 支持 **`Range` → 206**（实测）| 可续传 | 客户端带 `Range` 重试（§九）|

| 6 | 客户端超时设置过短 | 服务端仍在跑 | 客户端报超时 | 放宽 connect/read 超时；**只走异步接口**（§4.3）|

| 8 | 服务重启 → 客户端会话失效 | 需重新 initialize | 该轮工具报错 | 重连；任务状态见 19.4 |
| 9 | 同一主机开多个 agent 会话 | 服务端无状态 HTTP + 串行锁，能承受 | 各自独立 | 无身份区分（无鉴权）；同一工程别并行（§5.2）|
| 10 | 端口 50026 被别的进程占用 | uvicorn 启动失败 | 连不上 | 换 `MCP_PORT`；看启动日志 |
| 11 | 杀毒/安全软件拦截 exe 或入站 | 进程被杀或连接被丢 | 随机失败 | 加白名单（现场部署注意）|

| 43 | 两台机器跑同一工程 | 无工程级锁 → 可能互相覆盖 | 结果异常 | 纪律 + 命名规范（§5.2）|
| 44 | 客户端传本地路径（引擎机上不存在）| `FILE_NOT_FOUND` / 校验失败 | 明确错误码 | 先 `list_epp_projects` 列引擎机工程（§八）|
| 45 | 客户端点 `file://` URI | 指向**客户端本机** | 打不开/打开错文件 | 改用 token 链接（§九）|
| 46 | 请求 `Host` 被伪造 | **回落到本机地址**（实测 8 例）→ 链接不会被污染 | 无感 | 已保障（§2.3）|
| 47 | 机器时间被改 | token `expires_at` / TTL 判断异常 | 链接提前/延后失效 | 保持时间同步（NTP）|
