## 0. 背景：这份清单是被实测逼出来的

今天把 CST 5 个工具真正跑通（求解 / 导 S 参数 / 导远场），过程中卡住的三次，全部不是「工具坏了」，而是**工具面缺能力**：

| 卡点 | 现场经过 | 代价 |
|---|---|---|
| 不知道模型里有什么 | 想确认「哪个 `.cst` 有 farfield 监视器」，没有只读接口 ⇒ 只能**逐个求解**再看结果树 | 8 个模型 × 每个 1–3 分钟 |
| 任务发出去就收不回 | 用户说「不用执行了」时，CST/HFSS 侧**没有 list、也没有 cancel**（ADS 侧只有 `list_eda_tasks`） | 4 个任务继续烧 CPU/许可，只能等或重启服务 |
| 只想「看一眼」却要先解算 | 归档 `.cst` 必须开一次 CST 才解包，而唯一能开工程的手段是 `cst_solve_async`（含求解） | 一次 3 分钟求解只为解包 |

**选型口径**：① 优先复用既有资产（`TaskRunner`、`servers/cst/cst_worker.py` 的作业框架、`build_file_link`/`fetch_artifact` 产物链、既有绘图链）；② **不得改变既有工具的签名与返回契约**（签名漂移会打断调用方与仓库的守卫测试）；③ CST 侧新增一律 `cst_` 前缀；④ 跨引擎通用能力（任务列表/取消）在三族下**同名同义**。

## 1. P0：三件代码 + 一件 0 代码描述，都只动 `servers/cst/*`，成本小、收益直接

### 1.1 `cst_get_model_info(model_path)` — 只读模型体检

| 项 | 内容 |
|---|---|
| 要解决什么 | 「这个模型能不能导 S 参数 / 远场」在调用前就要能问出来，而不是靠试错 |
| 建议返回 | `solved`（是否已解）、`unpacked`（是否已解包/非归档）、`ports`（端口数，可从结果树 S 项推断）、`freq_range`、`monitors`（列表，含 `Farfield` 有无）、`result_items`（结果树前 N 项）、`notes`（读不到时的原因原文） |
| 实现要点 | worker 新增作业 `op="info"`，复用 `open_3d_results()` 读结果树 + 捕获归档异常（与 `detect_farfield()` 同思路）；**不求解、不开 GUI 会话** |
| 成本 | ≈60 行（worker）+ 1 个工具壳；单测：mock 结果树 3 例 + 归档 1 例 |
| 产出 | **一次秒级调用**替代今天的 8 次求解 |
| 验收 | 对 `demo_horn_24GHz.cst` / `Discone_antenna_38` 应报「有 farfield」；对 `Low Pass Filter（低通）` 应报「无 farfield、2 端口」；对未解包文件应报 `unpacked=false` 并给出原文，而不是抛错 |

对等物参照：HFSS 侧已有 `get_hfss_project_info`，CST 侧一直缺对称件 —— 这也是三族口径不对齐的一处。

### 1.2 `cst_task_list()` / `cst_task_cancel(task_id)` — 任务可管

| 项 | 内容 |
|---|---|
| 要解决什么 | 异步任务发出后既看不到全貌、也停不下来 |
| 建议返回 | `task_list`：`[{task_id, status, op, model_path, started_at, elapsed_seconds}]`；`task_cancel`：`{cancelled: true/false, reason}` |
| 实现要点 | `TaskRunner` 内部已有 `_tasks` 注册表与锁 ⇒ 加 `list()` / `cancel()` 两个方法；**取消语义要诚实**：正在子进程里跑的那一步无法真的打断 CST 求解，只能「标记取消 + 杀 worker 进程 + 如实说明」 |
| 前置改造 | ⚠️ 现状 `cst_api.py` 用 `subprocess.run()` 阻塞等待、**未留存 Popen/pid** ⇒ 「杀 worker 进程」没有 pid 可杀。cancel 的第一步是 `subprocess.run` → `subprocess.Popen`、把 pid 写进 task metadata、再加 kill 路径 |
| 成本 | `TaskRunner` 扩展 + 两条工具壳 ≈40 行，**再加一次 `subprocess.run→Popen` 改造（pid 留存）**；单测：排队中取消 / 运行中取消 / 已完成取消 3 例 |
| 产出 | 队列可见、可止损；今天那 4 个任务本可一次清掉 |
| 备注 | 建议**同时给 `hfss_*` 加同名两件**（HFSS 侧同样只有 `get_hfss_analysis_status`）；ADS 侧已有 `list_eda_tasks`，补 `cancel` 即可口径一致 |

**取消功能的两个工程要点（补充）**

1. **改 `Popen` 时别丢掉 `subprocess.run(timeout=)` 白送的两件事**：① 超时兜底 ② stdout/stderr 捕获 —— 后者正是今天「作业未产出结果（exit=1）」时那句 `File "…cst_worker.py", line 28 … SyntaxError` 的来源，丢了就等于把错误诊断能力一起丢了。建议 `Popen` + `communicate(timeout=)`，超时即 `kill()`；CST 子进程树不止一层（python worker → CST 引擎），必要时 `CREATE_NEW_PROCESS_GROUP` + `taskkill /T`。
2. **cancel 只能「尽力而为」，返回体要如实说明**：真正占资源的是 **CST 拉起的引擎进程**，杀掉 python worker 未必停得下正在跑的 CST 求解。判据：`tasklist | grep -i cst` —— 常驻的 3 个 Session-0 服务（`cstd.exe` / `CSTDCMainController_AMD64.exe` / `CSTDCSolverServer_AMD64.exe`）是背景，**多出来的才是这次会话**；返回里写清「worker 已终止 / CST 求解是否确认停止」。

### 1.3 `cst_open_project(model_path)` — 只打开并保存（= 解包），不求解

| 项 | 内容 |
|---|---|
| 要解决什么 | 归档 `.cst` 想解包/想变成可读，却只有「跑一次完整求解」这条路 |
| 建议返回 | `{success, model_path, unpacked: true, elapsed_seconds}` |
| 实现要点 | worker 新增 `op="open"`：`open_session()` → `prj.save()` → `close_session()`；复用已有 `to_writable_copy()`（桌面文件只读时自动拷副本） |
| 成本 | ≈25 行；单测 2 例（正常 / 打开失败） |
| 产出 | 秒级把模型变成「可读可导」，也顺手把只读模型变成可写副本 |
| 验收 | 对桌面拷来的归档 `.cst` 调用后：`.cst` 字节数变化 + 出现同名结果目录（今天的实测指纹：210,797 → 210,849 B） |

### 1.4 描述层补三条已知边界（0 代码，纯 docstring）

| 项 | 内容 |
|---|---|

| 产出 | 省掉对着报错猜原因的时间；也是 §6「错误可诊断」在描述层的落地 |

## 2. P1：输出与体验，日常最直观

### 2.1 `cst_list_results(model_path)` + `cst_plot_farfield(txt_path, cut="phi=0")`

- **痛点**：今天交付给你的是 **47 KB 的 ASCII 表格**；方向图本该看图。ADS 侧早有 `list_result_curves` + `turbocharts_convert` 的成图范式，**CST 侧没有对等物**。
- **建议**：`cst_list_results` 回结果树/产物清单（与 1.1 共用读取层）；`cst_plot_farfield` 解析远场 txt（列为 `Theta / Phi / Abs(Gain)[dBi] / Phase / Ax.Ratio`）出 **PNG**（极坐标切面 + 直角曲线各一张），走既有产物链返回可内嵌链接。
- **成本**：中（≈120–180 行，绘图链复用）；**产出**：chat 里直接看图，不用下载表格核对。
- **注意**：远场 txt 有 `frequency_minimum/centre/maximum` 多份，接口要显式选频点，避免「默认取第一份」的隐式行为。

### 2.2 `cst_export_*` 默认各写独立子目录（行为微调，非新工具）

- **痛点**：今天实测撞到 —— 同一目录连着导两个模型，第一个的 txt 被算进第二个的 `farfield_txts`（已修：导出前后做目录快照，只回本次新增/变化的文件）。
- **建议**：`output_dir` 缺省时落 `<模型目录>/<模型名>_exports/`，与"快照过滤"双保险。
- **成本**：3 行；**风险**：会改变默认落盘位置 ⇒ 属**行为变更**，建议在 docstring 里写明并在 `审查报告.md` 记一条。

### 2.3 三族口径统一（不是新工具，但直接影响使用体验）

今天同一次任务里出现了三种字段名指同一概念：`snp_path` / `farfield_txts` / `model_path`；`hint` 的取值集合也不完全一致。建议统一：

| 维度 | 建议口径 |
|---|---|
| 任务号 | 一律 `task_id`，前缀区分引擎（`cst-` / `hfss-` / `eda-`） |
| 产物 | 统一的 `artifacts: [{path, url, sha256, size_bytes}]`（复用 `build_file_link` / `fetch_artifact`），**旧的单值字段保留**为兼容字段 |
| 失败 | 统一的 `error_code` + `hint` + 可读 `message`；长任务一律带 `completed` / `outcome_known` |
| 文档 | `docs/TOOLS_API.md` 与 `docs/TOOL_INDEX.md`（生成物）同步 |

**成本**：中（一次性梳理 + 文档），**风险**：改返回体属契约变更 ⇒ 建议「加字段不删字段」的过渡策略。

### 2.4 `cst_export_snp` 改异步（与其余 4 个工具同范式）

- **现状**：`servers/cst/result_export.py:77` 走 `cst_runner.run_sync(..., timeout=900)` ⇒ **同步阻塞在工具调用里**。
- **两个后果**：① 不可取消（前置改造见 §1.2）；② **900 s 超过 Hermes 客户端单次调用的读取上限 300 s** —— 客户端会先断开而服务端继续跑完 ⇒ 模型大 / 盘慢时，用户看到的是「超时」，不是结果。
- **建议（二选一）**：
  1. 把 `timeout` 降回 <300 s（最小改动，但只是把「超时」提前，治不了根）；
  2. **统一成 `submit` + `query`**：新增 `cst_export_snp_query`（与 `cst_solve_query` / `cst_export_farfield_query` 同名同构），`cst_export_snp` 改为立即回 `task_id`。
- **成本**：小（≈30 行，复用 `cst_runner.submit` + `query_task`）。
- ⚠️ **风险**：方案 2 改的是**既有工具的返回契约**（`snp_path` → `task_id`）⇒ 要么按 §2.3 的「加字段不删字段」过渡，要么**新增** `cst_export_snp_async` 而保持 `cst_export_snp` 不动（更保守，推荐）。无论选哪个，都要走 §5 的改动面清单。

## 6. 验收口径（本清单里所有工具通用）

- **必须真调**：不接受「单测全绿」当结论 —— 今天 50 条单测全绿仍漏掉一个 3.6 语法问题，只有真调（`curl` 或客户端）才暴露。
- **产物要对得上物理**：例如 `get_model_info` 报「有 farfield」必须与 `cst_export_farfield` 真能产出 txt 一致；`plot_farfield` 的图要与 txt 峰值一致（今天实测对角喇叭：峰值 **+14.47 dBi @ θ=0°, φ=−90°**）。
- **数字锚点**（可作为回归基准）：低通 `.s2p` **160,792 B / 1001 点**；对角喇叭 `.s1p` **53,511 B / 1001 点**，\|S11\| 最低 **−28.2 dB @107.2 GHz**；`demo_horn_24GHz` 远场 txt **47,726 B / 312 行**；`Discone` 远场 **3 份（min/centre/max），各 405,230 B**。
- **错误可诊断**：失败必须带原文（形如 `Archived CST files are not supported…` / `run_solver returned False`），不允许只回一句「失败」。
